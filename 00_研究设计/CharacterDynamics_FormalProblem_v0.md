## 1. F0：系统问题与一个合法实例

用户要求的核心是**世界持续运行，人物有自己的生活与信息，作者可设关键要求而不枚举全部情境分支**。玩家是世界中的参与者，不是每个 NPC 活动的唯一中心。因果连续与体验上的起伏是两个目标，不能用一致性测试替代玩家体验。

一次问题实例至少给出以下输入，否则只能讨论想法，不能运行可复核比较：

| 输入 | 必须明确什么 | 缺失时 |
|---|---|---|
| domain / executor | 实体、合法状态、动作/技能、前提、时长、资源占用、真实效果、失败/部分效果及版本 | 不接受 LLM 声明的新能力 |
| 初态与角色 | 权威 W；每个角色自己的初始 O、模型 S、固定 P、任务及权限 | 不用全知 W 自动填 NPC 知识 |
| 时间与过程 | 物理时间单位、世界自然过程、外部输入来源、同刻排序、随机流 | 不默认“一次 LLM 调用=一个世界周期” |
| 作者要求 | 目标角色/对象、条件与期限、硬软、允许干预、锁定范围及失败分支 | 歧义须确认；不自行挑对算法有利的解释 |
| 控制与信息 | 玩家/NPC/导演各能读和改什么、观察路径、输入适配器 | 无授权不能调度他人的动作 |
| 比较口径 | 扰动、预算、成功证据、基线、劳动/运行成本、开发/验证分离 | 不把漂亮录像作为贡献证据 |

**MC 地狱门例子是用户的解释例，不是当前环境。**“100 周期内完成”首先要选物理 tick、模拟分钟或显式控制周期；不是模型调用计数。挖钻石路线和遇到岩浆后的浇筑路线可替换；打火石子任务可交错，但一个角色的互斥控制不能同时执行，共享资源也不能在两条支路各自花一次。

## 2. F0：状态、所有者与信息权限

为避免与现行 `X=appraisal` 混淆，用 `𝒳_t` 表示全系统配置，而不重定义 X：

```text
𝒳_t = (W_t, {O_i,t, S_i,t, P_i, R_i,t, H_i,t, C_i,t, Q_i,t}, K_t, L_t)
```

这只是职责分解，不要求创建同名 C++ 类。现行单角色系统有其中部分设施；通用多角色、永久账本与规划缓存尚未接成应用。

| 对象 | 含义 / 唯一权威 | 不能偷换成 |
|---|---|---|
| W | 游戏执行器拥有的客观状态、资源、地点、实体生命周期 | LLM 叙述、预测未来 |
| O_i | 角色 i 经合法通道获得的观察、信念、来源与 Known/Stale/Unknown | 全知 W；Known 也可能已错 |
| S_i / P_i | pin 模型的持久状态 / Personality；当前 P 固定，commitment 在 S 内 | 人类心理量表；P 不是目标集合 |
| R_i | 正在执行的动作及身份、目标、开始时刻、计划时长、elapsed、状态 | 每轮新建的同名动作 |
| H_i | i 合法收到的历史视图，允许压缩/遗忘 | 全局永久历史 L |
| C_i | 当前控制片段、截止/guard/适配器版本（低层应用提案） | 已承诺未来所有动作都执行 |
| Q_i | 角色规划/缓存/候选未来及其假设（提案） | W 真值、作者硬约束 |
| K | 唯一时钟、boundary 调度、运行队列及随机流 | Director 或 LLM 私有时钟 |
| L | 已提交实际事件与执行回执的可追溯账本（通用应用待建） | 可任意重写的故事文本 |

角色控制器输入只允许自己的 O/S/P/R/H、已授权任务、合法候选/技能目录。全知导演/评估器可在各自权限内读 W，不能因此把隐藏备用资源喂进 NPC 的候选构造。计划器也不能直接把“希望 B 愿意借出”写进 B 的 S。

任务能力、自主性和作者控制分别判断：作者赋予伐木职业/任务，可以测任务执行；不等于 NPC 自己形成了目标。作者亲写覆写可合法但必须记账，不计作自然自主行为收益。

## 3. F1：时间不是决策轮数

统一权威物理时间上至少区分四种量：世界推进 `Δt`、控制片段持续时间、规划器调用间隔、叙事进度（事件/阶段）。叙事进度可以另有索引，但不可拿它推进 World 时钟或结算动作。

- 高层规划器暂不调用时，已提交低层控制/RunningAction 与世界过程仍可继续。
- 用户的“保持 W 三周期”是控制例子；不是统一的最低三 tick、禁止紧急停机，或最优推理频率结论。
- 适配器必须声明控制起止、合法反馈、guard、取消条件和何时允许重新规划。即时物理安全停止不等待 LLM；也不能借安全 guard 偷读隐藏地图。
- 事件驱动长动作跨多个 boundary 保留同一身份和 elapsed。世界消息产生一个边界，不等于动作重新从零开始。
- deadline 的锚固定于已确认时刻/事件；重规划不会把期限顺延。语义中的 strict 时间先后与同刻 ledger sequence 分开。

现行房间 Runtime 的分钟单位与确定同刻优先级仍由 [Scheduler contract](Runtime_Scheduler_v1.md)拥有；新增应用若用 tick，必须提供明确单位映射，而不是另立隐含时钟。

## 4. F1：请求、世界转移、回执与反馈

抽象的 WorldStep 是域拥有的转移关系，不预设任何规划算法：

```text
(W', actual_events, outcomes) = WorldStep(W, admitted_controls, exogenous_inputs, Δt)
```

随机域还需声明随机流及状态；给定完整 checkpoint、相同输入与同随机流后才可要求可复算。其他 NPC/玩家输入按协议归入 controls 或 exogenous，不能在两处重复作用。`ΔW_external` 若使用，只是结算来源归属，不是可将非线性世界变化相加分解的向量，也不是已识别因果效应。

一次请求至少经过：

```text
proposal → schema/type/authority → current W start validation
         → accepted control → progress / possible interruption
         → real settlement → actual events + typed outcome
         → legal observation projection → model update / reconsideration
```

`accepted` 只说明启动准入，不说明最终成功。执行前拒绝、执行中阻塞、执行后部分效果、完成是不同回执；不能统一为“没成功，所以什么也没发生”。无效飞行请求不能冻结天气/其他角色/时间。只有在**启动前无任何世界副作用且不改变后续随机流消费**的条件下，拒绝请求与 null 的同 checkpoint 配对才可得到相同 W；O/S/history 仍可能因失败经验不同。这个等价性是带假设的性质，不是无条件承诺。

当前 canonical Runtime 的边界路径以真实代码为准：

1. Scheduler 前进到 t，确认 boundary/action 生命周期；模型对上一段 `[t0,t)` 做 continuous integration。
2. W 按同一边界推进，处理 @t 世界事件与动作 outcome；只投影角色合法接收的信息。
3. `ΔO → X appraisal → S impulse → commitment`；即时 self feedback 不重复放进 deferred queue，随后 consume transient inputs。
4. gate 按明确原因开放才走 `A^O → π → ActionIntent`；continue 保留原 R/progress，replace 需先 W validate，合法才中断/替换。

边界时的内部可观察时钟会投影到 O；不代表外部事件先于连续积分。物理 preemption 与主观 reconsideration 不混同：threshold 可以引发重考虑，但不必强制取消。本文不改变同刻 external interrupt/completion 的已有 contract。

“LLM 输出一次结构化动作”只覆盖 proposal。低层适配器、时长、guard、World 验证与反馈不能因合并为一次模型调用而消失；应用需验证其接口，而非让 LLM 自评已执行。

## 5. F1：作者意图、语义绑定与真正发生的点/线

**Typed IR 是检查后端，不是作者必须使用的创作界面。**作者无需亲自模拟粮食经济、为每个角色填写心情曲线。作者可表达：谁须遇到什么、哪些设定不能坏、哪些路径/实现方式允许、哪段亲写内容锁定；已有游戏机制负责资源/物理过程。

候选的语义管线是：

```text
author intent + role binding + permissions
  → 明确歧义 / 作者确认 / 注册识别规则与版本
  → 可执行状态、事件或过程约束
  → committed evidence → 判定及解释
```

| 层 | 必须保留的区别 | 准入证据 |
|---|---|---|
| 点的定义 | “B 发现 A 欺骗”这一模式 vs 某次实际发生 | 角色/命题绑定、识别规则、合法观察、event IDs、时间/sequence、规则版本 |
| 线的定义 | 事件顺序、离散阶段、允许路径、经定义 feature 曲线；不必是 numeric band | 时间/叙事轴、特征提取器、起止/自由区间与软硬约定 |
| 方法要求 | 完成地狱门 vs 必须由浇筑过程完成这一扇门 | 建造事件链、材料/操作者/生成方块与最终门框稳定 ID；`method=cast` 字符串不构成证明 |
| 锁定段 | 作者固定内容 vs 进入/执行条件 | guard、内容 hash、角色/道具前提、abort 与明确许可 fallback |
| 高层语义质量 | 检查器按规则判真 vs 规则是否代表作者想表达的戏剧意义 | 作者审阅正反例；如主张玩家体验，另需玩家证据 |

PlotPointSpec / Occurrence、Arc、Recognizer 等是可选表示，尚非现行类。一个多用途 Node 也可以记录来源，但必须区分 author requirement 与 planner-derived subgoal：选某个 method 后才需要的子任务，不能偷偷升级为作者永不可撤销的要求。

硬约束先决定可行集，软偏好只在允许集内排序；unknown 不等于可行、违约也不能用更高戏剧评分抵消。权限、安全、作者希望等不同“硬”来自不同 owner；放宽可选作者要求不自动获得越过安全边界的权利。

## 6. F1/F2 接缝：规划器、导演、当前控制与历史

| 对象 | 输入 / 输出 | 禁止跨越 |
|---|---|---|
| ActorPlanner | actor-local 输入与技能；候选计划、探索/执行请求、重新规划理由 | 用全知 W 提前完成发现；将他人同意写成 effect |
| Director | 作者目标、授权视图与干预目录；机会/作者操作 proposal 与风险证据 | 调度自主 NPC 全部未来动作、抹掉玩家成功结果 |
| Executor / adapter | 当前合法请求；进度、真实结算与反馈 | 把计划预期效果提交为事实 |
| Monitor | 经绑定的约束与已提交证据；见证/反例/unknown | 以搜索失败宣布过去已违约；负责替世界达成目标 |

规划器内可用 LLM、HTN、GOAP/A*、Node/Maze 或混合算法。用户先提递归 Node/多出口 Maze，随后质疑其过度结构化；因此本文不冻结 Maze，更不因换成 LLM 就取消执行契约。具体方法、局部/全局启发式、缓存与重规划触发属于 F2 待比较内容。

必须分开四类数据：**作者规定的允许未来**、**规划器预测的候选未来**、**本周期提交的控制**、**已经结算的历史**。当前派发不承诺未来动作全部成功；future edit 不删除 past。修复需重验资源、依赖、时长与真实 actor 信息，并保留仍合法 RunningAction progress，不能每周期整体重置。

世界路径存在 ≠ 角色知道路径 ≠ 角色愿意执行 ≠ 玩家不会破坏 ≠ 系统保证完成。超出搜索预算只报 `NO_PLAN_WITHIN_BUDGET`；完整有限域穷尽才可给不可达证明；在线 monitor 的 PENDING 可与规划器不可达结论同时成立。

### 三类不同的计算对象

以下对象必须分别定义域、信息权限、时间窗与证据，不能压成一个“可完成”状态：

1. **世界存在性可达：**对冻结的有限世界/动作模型、初态、资源与绝对 deadline `T`，是否存在一组合法 joint controls 及其 executor 转移，能在 `T` 及以前产生目标 witness（`∃`）。这只说明模型内有一条路径，不说明角色或玩家会选择它；有限搜索未穷尽时不得把未找到路径写成不可达。
2. **固定策略下的成功概率：**给定初态 `W0`、绝对 deadline `T`、actor/player 策略 `π` 与随机性/响应模型 `M`，计算 `Pr(success witness at or before T | W0,π,M)`。确定性单条 trace 只给该次执行 verdict；有限样本只能在明确的采样假设下给估计/置信区间，不能给无条件或确定性下界、鲁棒保证，也不代表真人响应概率。
3. **作者策略的鲁棒保证：**是否存在合法 Director 策略 `d`，使其只根据已授权历史选择已授权控制，并对冻结集合中所有允许的外部、玩家及其他角色响应都能保证不晚于 deadline 成功（`∃d ∀responses`）。`d` 是带信息权限的策略，不是预知未来的固定动作序列，也不取得控制 B 的权力。证明需要有效的有限博弈/模型检查及完整响应策略类；抽样全成功不能证明全称量词。若允许的 B 策略可始终拒绝，且不存在替代路径或许可干预，就不存在该鲁棒保证。Monitor 仍只判定已提交事实。

以下只核对已有头文件与本 reference，不新增接口要求，也不授权改动冻结 Kernel：

## 7. 性质、假设与最小反例（不是都已测试）

| 性质 | 必须挑战的反例 | 当前证据 / 未闭部分 |
|---|---|---|
| 信息不泄漏 | planner 知岩浆，角色尚未观察却已走浇筑路线 | 房间 O 边界有回归；通用 planner 未接入 |
| 权威状态与历史 | LLM 说门已造好；世界无对应方块/settlement | 原执行核有验证；MC 仅纸面例 |
| 时间持续 | 请求非法/LLM 未调用，世界应继续；同动作跨消息边界不重启 | 房间 scheduler 已实现；低层按键 adapter 待建 |
| 失败不抹效果 | 开始后工具损坏、材料消耗，不能当启动前拒绝 | 通用 executor 须注册部分效果；非全域已证明 |
| 重考虑可继续 | needs 触发后继续同动作并保留 progress | 原 Runtime 已有机制；本轮不修改 |
| 证据单次消费 | 同 boundary completion/rejection 的 ΔO 重投 | 原 Runtime 回归；独立 monitor 另有本轮多段修补 |
| 连续监测可靠 | 前段内部越界，后段安全；公共闭端点给两个值 | 独立 reference 本轮复现/回归，不是世界 dynamics 证明 |
| 作者过程可验证 | 最终门存在，却按矿镐路线造；标签自称浇筑 | provenance 绑定契约待实例化 |
| 候选不冒充历史 | 子目标、rollout 或 LLM 建议写入真实账本 | 现有设计分层；完整 fork/Director 尚无端到端证据 |
| 共享资源一致 | 两条“并行”支路都消费同一铁锭 | 规划域与执行器联合测试待建 |

## 8. 研究问题、细分阶段与当前成熟度
