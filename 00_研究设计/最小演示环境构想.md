# 最小演示环境构想：单角色 Character Dynamics Lab

记录日期：2026-09-02  
状态：**演示规格已细化；具体状态机制、动作策略与实验数据仍待定。用户将在 `E:\Character Dynamics Demo` 的独立 coding 会话中自行以现代 C++ 实现。**

## 目的

做一个“小房间 + 一个人 + 连续几天”的可回放 demo。它同时承担两种职责：

1. **实验装置**：受控地产生 `W/O/StateDelta/S/action` 轨迹，比较状态更新方法、基线、干预与消融；
2. **公开演示**：在实验稳定后，以最小可复现仓库展示“同一角色因经历与状态不同而做出不同微行为”。

它不是完整游戏，也不以做地图、UI 或多 NPC 社会模拟为第一目标。时间与界面并非装饰：应让人看见角色在几天内经历什么、知道什么、做了什么、哪些状态发生变化，以及这些变化如何影响下一动作。

## v0 场景边界

```text
一个房间（连续数天）
一个角色 A
少量对象：床、桌子、椅子、电脑、手机、灯、门
少量世界变量：日期/时钟、动作持续时间、角色当前位置
自然延伸场所：厕所、食堂或其他门外目的地（可先作为简化场景转换）
可选外部事件：消息/未回复、时间流逝、门外动静
```

`W` 保存对象状态、位置、时间、事件与动作合法性；角色只接收 `O` 中允许看见或收到的信息。角色并不直接改世界，而是从 affordance provider 给出的合法动作中产生分布，再由 world executor 结算。

场所仍是 W→O 的第一层过滤器：A 在某场所时，该场所变化进入候选观察流；具体哪些字段更新到 `O_A`，再由可见/可听/注意力等可配置规则决定。离开场所后，对应 O 视图保留并可随时间成为 `stale` 或 `unknown`。

### 分层时间调度（demo 约束）

demo 采用一个模拟时钟，但不采用“每一 tick 把 W/O/S/D/策略全部更新一次”的总循环。各部分有自己的触发条件和可配置周期：世界时钟、动作持续和排程事件更新 `W`；消息/暴露/场景变化优先刷新相关 `O` 字段，低频维护其 `stale`/`unknown`；每个 `S` 字段按自身的事件触发与恢复/累积速度更新；只有到决策点、动作完成或真正改变候选行为的事件时才计算 `D` 与 `π(A)`；UI 可独立按渲染频率显示。

数值周期先写入 scenario/config，而不当作已经成立的心理学公式。每次执行都记录模拟时间、触发来源、`Δt` 与被更新字段，使不同调度配置也能在同一 trace 上重放和比较。

这里的“调度”只规定**在模拟语义上何时应更新什么**，不要求 v0 解决在线 LLM API 的异步返回、并发、超时、重试、费用控制或玩家可见世界的滞后呈现。第一版先以同步规则、固定 fixture 或可替换的本地/预先生成算子跑通闭环；在线异步服务是跑起来之后再处理的工程层。用户提出的“行动酝酿层”“向玩家呈现一份落后于计算世界的副本”，以及 LLM 未返回时该角色显式显示“思考中”、暂停提交下一人物动作，均保留为后续候选；当前不新增顶层状态或 demo 子系统。

当前代码归属目录是 `E:\Character Dynamics Demo`；研究设计、文献、原始材料仍以本仓库为准。项目内此前的 `demo/` 浏览器脚手架已删除；它不是用户将要编写的 v0，也不应被当作研究实现或 C++ 参考。本研究会话不继续改动用户将在独立 coding 会话中编写的 C++ 代码。

另有 [Demo codex-generated](../Demo%20codex-generated/)：它是完全独立的 Codex C++17 参考实现，用来让用户阅读一条有限规则下的 `W→O→X→S→D→A→W` 链，不读取、复制或修改 `E:\Character Dynamics Demo`，也不充当研究结果或用户亲写 demo。

## 连续数日的可展示轨迹

每一轮至少展示：

```text
Day / clock / 当前场所与对象状态（W）
角色本轮可知的信息（O，含 fresh / stale / unknown）
事件的结构化意义（X）
启用状态字段及其变化原因（S）
本轮决策上下文与候选动作分布（D / π(A)）
选中的人物级动作、世界原子效果与来源链
```

第一批行为链不是最终心理学规则，而是 demo 必须能承载、用来检验状态/动作接口是否真的连通的**情境要求**：

```text
无聊 / 低投入 → 玩电脑或玩手机
长时间设备使用 → 不适、疲劳或睡意上升 → 更可能睡觉/休息
感到自己拖延或懒散太久 → 焦虑/紧迫感上升 → 可能短时学习
产生购买欲 → 在手机/电脑可用、且角色知道相关条件时 → 可选择手机/电脑上的浏览或网购行为
```

这些链条必须允许竞争和失败：焦虑不保证一定学习，疲劳也不必每次立刻睡；它们只要求状态的改变能让动作分布出现可追踪的方向变化。具体使用哪些 X/S 字段、怎样更新、每种变化的大小和阈值，留给状态机制阅读与实现配置决定。

“网购”在这里仅是手机/电脑使用可以承载的一种说明，不应独立反客为主地决定场景设计；若 v0 保留它，其订单等后果才需要进入 W。

## 从现实场景长出动作，而不是反过来

设计顺序固定为：

```text
先选一个现实中自然成立的生活场景
→ 放入该场景真实会有的对象、对象状态与场景出口
→ 看见对象即可列出自然基础行为和自然组合行为
→ 再冻结有限的 A^W / A^O 作为实验动作集
```

例如手机/电脑自然支持浏览、娱乐、联系和可能的购物；床自然支持休息/睡眠；桌子自然支持坐下学习；门首先是场景转换接口，可自然导出“出去上厕所”“出去吃饭”“离开再返回”等，而不是只设计“开门/关门”这种脱离生活目的的动作。房间外可先做成简化目的地和时间/身体状态变化，不必立刻展开开放世界。

这条原则不是“动作越多越好”。最终仍只保留能在该场景中自然成立、能被 W 结算、且能用于比较状态驱动行为分布的少量动作。

## 用 P 观察不同人物轨迹

每条单独轨迹内 `P` 保持固定；但同一初始世界、同一事件 trace、同一随机设置可以运行多次，仅改 P 配置。这样可以直接比较不同人物在同样几天里如何：

```text
解释同一事件（X）
→ 积累/恢复不同状态（S）
→ 在手机、学习、休息、出门等行为间形成不同轨迹
```

这不是 P 学习，也不预设“某个参数等于某种人格标签”。参数的选择和数值留给机制阅读与实验配置冻结。

## 实验要回答什么

同一终局、不同历史或可知信息时，比较：

```text
persona only
persona + raw history
persona + summary
persona + Character State v0
```

观察真实/预设目标动作的排序与概率、干预后的分布方向，以及关闭某个 state module/operator 后的变化。demo 的场景脚本和随机种子必须固定，以便不同版本可重放。

## 建议的最小运行模式

```text
Replay mode
固定事件 trace → 更新状态 → 输出各动作概率 → 与 trace 中目标动作比较

Intervention mode
复制同一终局 → 只改一段历史或观察 mask → 对比 state/action distribution

Simulation mode（后置）
按分布采样动作 → world executor 结算 → 继续下一 tick
```
