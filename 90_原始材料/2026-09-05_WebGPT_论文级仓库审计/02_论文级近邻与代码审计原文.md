## 2.1 第一处硬错误：现在的 `A^O` 其实在偷看 `W`

你目前：

```cpp
for (ActionType action : world.available_actions())
```

然后才生成 `Observation.known_actions`。

而 `world.available_actions()` 又调用：

```cpp
can_execute(action)
```

其中会根据真实世界检查：

```cpp
wallet >= 30
room.light_on
active_task_for(action) != nullptr
alarm_ringing
curtain_open
...
```

这就意味着：

**角色的主观动作空间是在 W 已经知道真相之后生成的。**

最漂亮的反例就是钱包。

你的 `O` 根本没有把钱包金额写进去。

但是如果钱包从 40 变成 20：

```text
ShopOnPhone
```

会直接从 `A^O` 消失。

于是角色虽然“不知道钱包多少钱”，却可以通过：

> “咦，购物按钮怎么消失了？”

反推出隐藏真相。

这正是信息泄漏。

所以真正应该是：

```text
O
↓
角色知道：我有手机
角色认为：手机可以购物
↓
A^O contains ShopOnPhone

             W
             ↓
实际 wallet = 20
             ↓
attempt ShopOnPhone
             ↓
W rejects
             ↓
允许反馈进入 O
```

而不是：

```text
W: wallet=20
↓
把 ShopOnPhone 从菜单删了
↓
角色神秘地知道不能购物
```

这是**Paper-0 之前必须修**的。

因为如果连 `W ≠ O` 都没有真正做到，你以后再做“信息干预”，结果根本不能解释。

# 三、第二处甚至更严重：`commitment` 直接从 W 穿透进 S

实际执行链现在是：

```text
refresh O
→ X
→ update S
→ decide
→ sample
→ W settle
→ update_commitment(state, WorldOutcome)
```

这里最后一步非常危险。

`update_commitment()` 直接读：

```cpp
if (outcome.task_completed) {
    state.commitment = {};
}
```

也就是说：

> 世界知道任务完成了
> → 角色的 commitment 立刻消失

**完全没经过 O。**

这和你自己设计的：

```text
W → O → X → S
```

正面冲突。

而且你 TODO 里已经想做一个非常好的实验：

> 世界里任务实际上已经完成，但角色是否收到完成确认不同。

现在这个实验压根跑不了。

因为即使不给角色看完成消息：

```text
W: completed
↓
WorldOutcome.task_completed=true
↓
commitment直接清空
```

角色依然莫名其妙地“知道自己不用管了”。

更有意思的是，你当前的 smoke test 还把这件事锁成了正确行为：

```cpp
completes_task_with_variable_effort =
    ...
    && commitment_state.commitment.status == None;
```

所以现在不只是“实现有旁路”，而是：

**测试正在保护这个旁路。**

这个我作为导师会直接定性：

> **E0 之前不允许开始任何正式 W/O intervention。先把 commitment 的信息入口改正确。**

正确结构应该是：

```text
W settlement
    ↓
typed perceptible feedback
    ↓
O
    ↓
commitment updater
```

如果“自己刚做完作业”在该场景中理应立即知道，完全没问题。

那你就在 perception rule 中声明：

```text
self-action completion feedback is immediately observable
```

而不是让 W 私下穿墙修改心理状态。

这两个概念差很多。

# 四、还有一个容易被你忽略的问题：broken、absent、unknown 现在被揉成一团

当前刷新 O 时：

```cpp
if (object.usable)
```

才会把对象当成 visible/known。

因此：

```text
电脑不存在
电脑在眼前但是坏了
电脑存在但被遮住
电脑以前见过现在不知道在哪
```

在当前实现里很容易坍缩成类似的 stale/unavailable 状态。

而这四个东西对人物完全不一样。

比如：

> 电脑就在桌上，但是按开机键没反应。

这应该是：

```text
O: computer present
O: usability maybe believed=true
attempt UseComputer
W: broken
W rejects
O: learns failure
```

而不是：

```text
computer.usable=false
→ 电脑从角色视觉里凭空消失
```

所以 Q04 不是工程洁癖。

**它其实就是你这个研究最核心的 experimental identifiability。**

# 七、LIGHT：这是现在最值得你先读的，而且它比我上次说得还重要

LIGHT 不是一个“顺便可以拿数据”的东西。

它是你必须在 Related Work 和实验设计里正面承认的**直接前驱**。

原始 LIGHT 建了一个大型 fantasy text-adventure 世界，包含 663 个地点、3462 个对象、1755 类角色，以及大约 11000 个由 crowdworkers 扮演角色产生的交互 episode。人物不只是说话，还会执行物理动作和 emote；对象带 affordance，物理动作会改变底层世界。([ParlAI][1])

这件事为什么对你很重要？

因为它已经做了：

```text
persona
+ current world
+ objects
+ dialogue/history
+ previous actions
→ predict next action / utterance
```

所以：

> “把人物放进一个有 object/world/action 的环境里预测行为”

**绝对不能再作为你的创新。**

LIGHT 已经做了。

而且他们明确发现 world grounding、persona、objects、history 等上下文有助于行为预测。其 action prediction 还直接在合法候选里做 ranking。([ACL Anthology][2])

但是——这里恰好出现了你真正不同的位置。

### LIGHT 的 action candidate 更接近 `A^W`

它会根据底层世界规则过滤合法动作。

例如某物体不可拿、某行为前置条件不满足，那么它不是 valid action。

这对 text adventure 非常合理。

但如果你研究的是：

> **角色知道什么**

那这恰恰不够。

因为：

```text
engine knows impossible
```

不等于：

```text
character knows impossible
```

也就是说：

> LIGHT 有局部 world grounding，但它并没有把“权威 W”和“可错误、可陈旧的 O”当作研究对象分开。

因此我现在会这样定位它：

> **LIGHT 是你 `W + Action + external prediction` 这一侧的最强近邻，但不是 `W/O/S` 信息边界机制的等价工作。**

这才是机制级比较。

不是：

> LIGHT 有 world，所以跟你一样。

也不是：

> LIGHT 没有 S，所以跟你不一样。

而是看因果位置。

## LIGHT Quests 更有意思，但也暴露一个数据问题

后续 LIGHT Quests 加了自然语言 motivation / goal 和 human expert demonstrations，还专门在 held-out expert demonstrations 上评估 agent。([ACL Anthology][3])

这听起来简直是为你准备的。

但仔细看数据后，问题出现了：

训练/验证/测试有约 1800/100/211 条 human expert demonstrations，平均 demonstration 长约 12.92 turn；然而平均**物理 action sequence 只有约 2.18**，其余大量是 dialogue。([ACL Anthology][4])

这对你特别关键。

因为你的 S 想研究的是：

> 持续状态如何积累并影响后续行为。

如果每条轨迹只有两三个真正物理动作：

**长期状态还没来得及“动态”，episode 就结束了。**

所以我不再像上一轮那样简单说：

> “LIGHT 很适合，拿来做 A*。”

更准确是：

> **LIGHT 值得立即做 T0c feasibility audit，但不能在审计前宣布它就是最终数据集。**

而且千万不要干一件事：

> 把 LIGHT 的几千种自然 action 强行压成你小房间的 16 类。

LIGHT Quests 的总体 action vocabulary 很大，engine 每个状态再给合法候选。([ACL Anthology][4])

更合理的评测可能是：

```text
给定该 turn 的 candidate actions
→ 给真实 human action 排名 / probability
```

而不是先压成：

```text
Study / Rest / Phone / ...
```

否则你为了适配自己模型，把最宝贵的真实行为语义先扔了。

LIGHT 的代码仓库现在已经 archived/read-only，所以我也**不建议你把它搬过来取代自己的 C++ world**；它更适合数据和实验协议借鉴。([GitHub][5])

# 八、PersonaForge：这是“你如果继续说动态心理状态就是贡献，会直接撞上”的论文

PersonaForge 是 2026 Findings ACL 的新工作。

```text

```

动态状态里明确有：

```text

```

并在交互后持续更新。论文还做双过程机制，在关键交互时先 internal reasoning，再生成外部表达。([ACL Anthology][6])

所以如果你以后写：

> “传统角色人格是静态的，我们首次引入随交互更新的动态状态。”

**直接死。**

PersonaForge 已经做了，而且实验比你现在成熟得多。

但是它和你也不是“机制等价”。

PersonaForge 的 dynamic state 所处位置大概是：

```text
conversation
→ update mood / energy / relationship
→ influence next textual response
```

而你的目标是：

```text
authoritative W
→ role-specific O
→ semantic X
→ persistent S
→ action distribution
→ W settlement
```

它没有你现在强调的：

```text
W truth ≠ role belief O
```

也没有“世界结算后的 hidden fact 不应穿透心理”的实验问题。

它主要评价的是 personality consistency、style、defense mechanism、drift、recovery，而不是：

> **给定 state 后，完整历史还能不能显著提高下一行动预测？** ([ACL Anthology][6])

所以它真正威胁的是：

> **动态状态/persona 的新颖性。**

不是：

> **你的 predictive-state identification 问题。**

## PersonaForge 给你的一个非常重要的负面启示：S 绝对不能越加越多

这篇论文我认为你最该抄的，不是它的心理理论。

是它的**state dimensionality ablation**。

论文比较过状态维度扩展。

原始 3 维：

```text

energy
intimacy
```

表现最好。

扩成 5 维、7 维后，persona consistency 明显下降，drift 显著上升；作者把这解释成 state thrashing / prompt dilution 一类问题。([ACL Anthology][6])

注意：

这**不能证明“三维状态是宇宙最优”**。

它的 prompt、模型、任务都有特定条件。

但它对你是一个很强的先验警告：

> **“状态越丰富，人物越真实”根本没有理由成立。**

所以以后你再想加：

```text
自尊
羞耻
孤独
自我效能
依恋
长期焦虑
社交安全感
……
```

我会先问：

> **哪个实验结果要求你加？**

答不出来，不准加。

这正好反过来支持你现在的研究纪律：

**S 的成员资格应该由预测贡献决定，而不是由心理学百科决定。**

这一点我现在会强制你守。

ThinkPersona 也是 2026 ACL。

它从大量真实公开访谈构建 Persona Graph，包含五类内容：

```text
Basic Information
Value System
Relationships
Life Events
Event Influence
```

数据源包括约 1201 个真实人物访谈，最终形成大量结构化 persona/QA 数据。([ACL Anthology][8])

它的核心不是：

```text
state_t → state_t+1
```

而是：

```text
long-term biography/history
→ graph extraction
→ retrieve relevant entities/relations/events
→ reasoning chain
→ answer
```

所以：

**它不等于你的 S。**

更准确说，它比较像你未来可能有的：

```text
P
+
long-term event/provenance memory
+
structured history baseline
```

它甚至在 limitations/future work 里明确承认，目前 graph 主要服务静态知识/逻辑链，将来还需要动态 long-term memory。([ACL Anthology][8])

所以如果有人说：

> ThinkPersona 有 graph，所以你 state 被做了。

这是我们现在明确禁止的**标签级错误比较**。

---

## 但是 ThinkPersona 对你构成另一个很实际的压力：你的“strong summary”还不够 strong

你现在 baseline 想要：

```text
persona only
raw history
strong summary
state
```

这是正确方向。

但如果你最终拿：

> “LLM 总结一段历史”

当唯一强压缩基线，然后 Character State 赢了，

我作为 reviewer 会问：

> 为什么不用结构化事件图？

ThinkPersona 已经说明：

**人物历史完全可以不是一大段 prose summary，而是结构化关系/事件图。**其 graph + reasoning 的消融也显示结构化 grounding 会影响一致性表现。([ACL Anthology][8])

因此你将来必须有一个比“普通 summary”更狠的 baseline。

可能叫：

```text
Structured History
```

它可以比 ThinkPersona 简单得多，不需要 Neo4j。

例如：

```text
event
actor
target
outcome
time
known_by
```

就行。

否则你的 state 赢 summary，只能证明：

> “结构化表示比一段自然语言摘要好。”

而不是：

> “持续动力学 state 有价值。”

这就是精细归因。

# 十、AdaMARP：别被“dynamic multi-agent environment”几个字骗着跟它走

AdaMARP 也是 2026 Findings ACL。

它做的是多角色 role-playing orchestration。

轨迹里明确交织：

```text
[Thought]
(Action)
<Environment>
Speech
```

还有一个 Scene Manager 来：

```text
init_scene
pick_speaker
switch_scene
add_role
end
```

并让不同角色有 profile、scene-dependent motivation，管理多人交互和剧情推进。([ACL Anthology][9])

这听上去跟你未来的多角色系统很像。

但仔细看机制：

AdaMARP 的全局 interaction state 主要是：

```text
active roles
+
dialogue/history
```

current scene/environment 在很大程度上通过 manager 输出文本并继续留在 history 中，而不是你的这种：

```text
typed authoritative W
→ precondition check
→ settlement
```

其主要评价也是：

```text
character consistency
environment grounding
interpersonal interaction
narrative progression
instruction compliance
```

然后用 trajectory-level LLM judge 和人类偏好辅助。([ACL Anthology][9])

所以：

> AdaMARP 的 `<Environment>` **不能直接等同于你的 W**。

它是“叙事环境更新”。

你的 W 是：

> “如果角色想购物但余额不足，结算器必须拒绝。”

两者因果职责不一样。

而且 AdaMARP 的 manager context 非常贵，20-turn trajectory 就会累积非常大的输入上下文。([ACL Anthology][9])

这反过来可能支持你以后“显式状态减少全历史维护成本”的工程动机。

但现在：

**不准你实现 Scene Manager。**

AdaMARP 当前公开仓库甚至还主要处于 Coming Soon / 尚未完整释码状态。([GitHub][10])

所以工程上现在也没什么值得你马上搬。

# 十二、现在继续清理几个你项目里很深的误区

| 误区                                        | 我要你改成什么                                                                       |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| “S 比完整历史预测更准，就证明 S 含有更多信息”                | **错。若 S 是 H 的确定函数，信息不可能凭空增加。赢 H 说明有限模型下的压缩、去噪、inductive bias 或 context 限制更好** |
| “S 必须打败 raw history 才算有价值”                | **也不完全对。若性能近似但 token/延迟/可控性大幅改善，也有工程价值**                                      |
| “人类评分没用”                                  | **太绝对。它不能识别内部机制，但可以测用户体验/可信度，应该是次指标，不是主机制证据**                                 |
| “65,536 行 batch 已经很多数据了”                  | **不是。它是同一规则系统产生的高度相关 synthetic decisions，科学意义上的独立样本数绝不能按 65,536 算**           |
| “E0 干预跑通，就证明状态有效”                         | **只证明 wiring / architecture 没坏；因为 π 本来就是你手写消费 S 的**                           |
| “LIGHT 有 W，所以已经做了我们的 W/O”                 | **不对。它有 world grounding，但 valid action 倾向由真 W 提供，没有你要研究的 stale/mistaken O**   |
| “PersonaForge 有 dynamic state，所以我们的 S 没了” | **不对。它占的是动态 state 这一概念；你的问题应转为 state 是否是外部行为预测的必要/近充分中介**                     |
| “ThinkPersona 静态，不重要”                     | **错。它是非常危险的 structured-history baseline**                                     |
| “为了验证完整系统，先把二阶 ToM、多角色、P 漂移都补齐”           | **严格禁止。这会让变量数量超过你能做因果归因的能力**                                                  |

这里第一条特别重要。

你现在研究问题里写：

$$
p(A_{t+1}\mid H^{obs}_{\le t},O_t,P)
\approx
p(A_{t+1}\mid S_t,O_t,P)
$$

这个 formulation **比“state 比 history 准”科学得多。**

真正的问题叫：

> **predictive sufficiency。**

也就是：

> 已经给你 S 以后，完整历史还能额外告诉你多少关于下一行为的信息？

这才漂亮。

理想结果甚至不一定是：

```text
S accuracy > history
```

而可以是：

```text
History: 0.91
S:       0.90
S+History: 0.91
```

同时：

```text
S token = 5%
S latency = 20%
```

那已经非常有意思。

它说明：

> **S 把历史中绝大多数与下一行为有关的信息压进了一个紧凑表示。**

反而如果：

```text
S = 0.70
S+History = 0.92
```

说明：

> 你这个 S 丢掉了大量行为相关历史。

这比“NPC 看着还挺像人”狠太多。

# 十三、还有一个你以后必须加的杀手级消融：`shuffle-S`

假设：

```text
X 很聪明
π 也很聪明
S 在中间摆着
```

系统最后预测不错。

你怎么知道 S 真有用？

直接干一件事：

```text
episode A:
O_A
S_A
P_A

把 S_A 换成 S_B
```

然后：

```text
π(A | O_A, S_B, P_A)
```

如果行为分布几乎不动：

**S 是装饰品。**

这比看 S 数值轨迹漂不漂亮狠得多。

而且这个实验几乎不要成本。

所以我会把：

```text
full S
no S
naive-S
shuffled-S
```

放进未来正式实验。

PersonaForge 的 dimensionality ablation 已经提醒了你：

**一个 state 模块存在，不等于它在 causally carrying information。** ([ACL Anthology][6])

# 十五、我现在愿意替你守住的锚

information boundary

# 十六、如果这是我的项目，从明天开始我只允许做这 5 件事

1. **冻结 Paper-0 的一页问题卡，立即停止泛扩张。** 把上面的锚写成正式 RQ，明确这一轮不做 Inverse、不做多角色、不做二阶 ToM、不做 P 漂移、不做 AdaMARP 式 Scene Manager、不继续扩心理状态、不继续研究 Q01 的高级分段曲线。把 LIGHT、PersonaForge、ThinkPersona、AdaMARP 按“所有权—输入—更新—持续性—因果位置—输出—实验”正式放进机制比较矩阵。此后一篇新论文只有在直接碰到这个 RQ 时才读；剩下那三十多篇 Game AI Pro 不准为了“读完”而读完。

2. **先修两个会毁掉实验的旁路，然后把它们变成自动测试。** 第一处是 `A^O`：由 O 中已知/相信的 object affordance 和 believed precondition 生成，W 只负责最终 accept/reject；先做“钱包隐藏但 ShopOnPhone 候选不应神秘消失”的测试。第二处是 commitment：禁止 `WorldOutcome → S` 直接写入，必须走可感知反馈；做“W 已完成但 O 未收到确认时，commitment 不应自动清空”的测试。同时明确 exact task progress 到底是否有可见 UI，否则不要每轮把真实 float 标成 `direct_room_visual`。这一步不过，后面全部停。

3. **只实现一个真正的 `X→S` 切片，不准一次重构九个状态。** 我建议用 task/commitment 场景。X 先只做 `goal_relevance` 与 `goal_congruence/obstruction`；如实验确实需要，再加 `controllability`。S 先挑 `task_pressure` 加 commitment 这一条链。保留当前 `event→StateDelta` 作为 baseline。首版甚至不要急着接 LLM：先用 deterministic rule 把 X 的语义边界验证清楚，等结构稳定后再把 `I(ΔO,O,S,P)→X` 换成 LLM。验收必须出现“同一个动作因为目标/结果不同而产生不同 X”，而不是永远固定 `StudyFocused→pressure -0.15`。

4. **跑 E0：只做机制完整性和信息边界干预，不把结果冒充论文结论。** 设计 paired traces：不同历史最终收敛到同一个当前 W/O，看看 S 是否保存历史并导致不同 π；相同 W 改 O mask，行为只能通过 O 改变；相同 O/P、只改隐藏 W，π 在获得反馈前必须相同；再做 shuffled-S。E0 的意义只有一个——确认你声称的链真的存在，而且没有旁路。如果 E0 都过不了，禁止找模型、禁止拿大数据，回来修架构。

5. **并行只做一个外部数据任务：T0c LIGHT 审计；通过才进入 E1。** 抽 30–50 条 original LIGHT 和 LIGHT Quests human episodes，不训练模型，只核 actor、turn、persona/motivation、当前 world、历史、真实下一 action、每步 valid `A^W`、能否恢复 role-specific `O`、是否有未来泄漏、轨迹是否足够长。不要把它们压成你自己的 16 个动作，而是优先评估真实 human action 在每步候选里的 NLL/rank。如果 LIGHT 因为 action 太短或 O 无法恢复而失败，就把失败记下来；**不准为了适配数据篡改 W/O 定义。** 下一步我会更倾向于跟导师讨论一个小型受控 human-choice 数据采集，在伦理/知情同意要求下直接让人类在你的有限世界连续做选择，而不是继续无休止地搜一个“刚好完美”的公开数据集。

这五件事之前，**你不应该再实现任何“让 Character Dynamics 更完整”的功能。**

你现在已经很会做“完整”。

下一阶段科研真正要练的是：

> **删除 80% 的可能性，只留下一个别人能把你打输的问题。**

而且我现在认为你已经找到这个问题了。

如果最后实验显示：

```text
strong structured history
```

和

```text
raw history
```

都明显优于你的 `S`，

那我们就承认：

> **当前这套 Character State 没有成为行为相关历史的好压缩。**

然后根据结果改 S。

如果 `S` 打平 strong history，却成本低很多：

这是系统结果。

如果 `S` 不仅紧凑，而且 shuffled-S 显著掉、history 在给定 S 后几乎不再提供额外收益：

**那时候，你这个项目才第一次真正从“一个很有意思的架构想法”跨进“有研究证据的 Character Dynamics”。**

而我接下来会按这个锚拦你。你如果突然说“要不我们先把三阶 ToM/多角色/人格漂移做了”，在没有新实验理由之前，我的答案会直接是：**不做。**
