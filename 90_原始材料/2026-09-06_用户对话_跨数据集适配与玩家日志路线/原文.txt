Step 6：建立明确的删改规则

我建议以后 mechanism evolution 直接有这种表：

现象	默认动作
字段几乎不变化	查 updater；无理论/数据需求则删
字段变化但 π 不变	查 policy coupling；仍无增益则删
大量 clamp	改尺度/函数

跨数据集方向一致	提升为 core candidate

加 history 后仍大幅提升	S 表示不足
random/permuted S 一样	S 没实际作用

这样我们以后改机制就不是：

对，而且你这一步其实把“只是做 replay”推进成了更像真正的 mechanism identification。

因为如果我们只是照着数据集把当时出现过的 object 原样还原，确实有一个很严重的问题：

角色选了 A，到底是因为机制真的偏向 A，还是因为现场根本没别的可选？

这个问题不解决，π(A) 再漂亮也可能只是被 action support 限死了。

所以我现在会把每个数据集对应的场景构造分成两层，而不是只做一个 faithful replay。

第一层是 factual scene：尽可能忠实还原数据里当时确实存在、角色确实能接触到的东西。这个层只负责回答“我们的机制能不能解释真实行为”。

第二层是 expanded diagnostic scene：在不破坏原任务语义的前提下，加入一批额外但合理的 object / affordance / actions，让机制真的有选择。这个层负责回答“机制为什么选这个，而不是只是没得选”。

这两层不能混着当 ground truth。

比如原日志是：

宿舍
电脑
手机
作业
→ 玩家最后去玩手机

如果我们只重建：

电脑
手机
作业

然后机制也选手机，这说明不了太多。

expanded scene 可以加：

床
零食
书
音乐播放器
洗澡
聊天对象
出门

甚至一些和原行为竞争但语义不同的选项。

然后看：

当前 S / P / O
↓
为什么手机仍然高？
为什么床不是第一？
为什么学习不是第一？

这时候我们才真正开始观察 mechanism structure。

但这里有一个很重要的边界：

新加 object 不能被当成“真实人当时也有这些选择”的事实。

它们是diagnostic interventions。

所以以后每个 episode 应该同时有：

factual_support
expanded_support

而不是只有一个 A^O。

我甚至建议明确写成：

A_factual
A_expanded

前者来自数据，后者来自我们为了诊断机制构造的合理超集。

然后实验分别问两件事：

factual replay:
真实动作 A* 在不在高概率区域？

expanded diagnostic:
加入其他合理选择后，机制是否仍表现出合理偏好结构？

第二个没有真人 ground truth，所以不能用来证明“人真的会这样选”，但非常适合调机制。

这正好对应你说的“循环中找到比较合理的参数或者机制结构”。

其实这已经很像 system identification / model selection 了。

我们不是在问：

哪个参数最像心理学真值？

而是在问：

哪一套结构在多种外部轨迹和受控选择扩展下，既能解释真实行为，又不会因为加几个合理 alternative 就崩掉？

这才是很有意义的 criterion。

具体可以这样循环：

1. 从外部数据恢复 factual scene
2. 构建 expanded scene
3. 跑当前机制
4. 看真实 A* 排名
5. 看新增 object 是否把 π 搅乱
6. 做 sensitivity / ablation
7. 找 dead field / dominant field / saturated field
8. 改 updater / utility / timing / field structure
9. 在 dev episodes 上重跑
10. 换一批 episode 再验

这里“更多 object 导致机制选择别的”不是坏事，反而是我们最想看到的诊断信号。

比如加入：

bed
phone
snack
friend_message

以后机制从：

study 0.55
phone 0.35

变成：

bed 0.60
study 0.20
phone 0.15

那我们就要问：

是 fatigue 权重太大？
recovery action 的 utility 曲线太陡？
task_pressure 没有参与竞争？
还是本来这个状态下休息就应该是合理行为？

这才是机制研究。

而且 object 超集最好不是 LLM 随便凭空造。

我建议来源分三级：

Level 1：数据中真实出现
Level 2：同一游戏/场景 ontology 中存在，但该 episode 未使用
Level 3：LLM 提出的 plausible diagnostic object

Level 3 可以用，但必须标成 synthetic diagnostic。

这样以后我们知道：

哪些选择是环境真实提供的，哪些是我们为了测试机制故意塞进去的。

最后还有一个很关键的事情。

我们不能每次为了让真实 A* 排第一就调参数。

那样会变成：

看答案 → 调函数 → 把答案顶上去。

正确目标应该是多目标的：

factual A* prediction 不差；
expanded scene 下不被无关 distractor 随便扰乱；
有意义 alternative 出现时概率能合理变化；
字段 sensitivity 不为零；
ablation 能说明哪些字段真的有用；
不同数据集上不需要完全重写机制；
参数不要极端依赖单一 episode。

所以真正要找的不是“能拟合动作的参数”，而是：

跨 episode、跨场景、跨数据集还能保持合理响应结构的一套最小机制。

这就很接近我们现在真正该做的研究对象了。

我觉得接下来代码层最好直接围绕这个设计：

DatasetAdapter
→ SceneBuilder
   ├─ factual_scene
   └─ expanded_scene
→ CharacterDynamics
→ Trace
→ DiagnosticReport

而不是继续在 C++ room 里手写更多固定物体。

这条路线我现在非常认可。
