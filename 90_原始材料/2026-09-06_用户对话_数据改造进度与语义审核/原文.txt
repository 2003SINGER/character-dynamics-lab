所以第一批 ClubFloyd / LIGHT 完全可以这样搞：
```
raw trajectory
↓

↓

↓

```
关键是：我们处理完以后，结果要变成死数据/死规则，而不是每次跑实验时重新让 AI 判断。
比如我们人工处理 50 条：
```
source_event:
  raw: "You finally finish the assignment."

semantic_annotation:
  event_type: task_completion
  goal_relevance: high
  interruption: false
  perceived_progress: completed
  confidence: high

provenance:
  kind: llm_inferred
  model: GPT-5.6 Sol
  annotation_version: semantic_v0
```
保存下来。
下一轮实验：
```

不调用 Luna
直接读 semantic_v0
```
然后如果实验暴露出：
task_completion 这个语义划分太粗，
我们再人工修：
```
semantic_v0
→ semantic_v1
```
并记录哪些条目变了。
这和我们前面说的机制 loop 完全一致。
而且第一批我甚至不建议追求全自动化。
20～50 条数据最重要的是搞懂：
数据到底长什么样，我们究竟需要什么语义字段。
如果一开始就先写：
```
ClubFloydSemanticParserV1
```
很可能我们连 ontology 都没搞明白，就已经把错误假设写进程序了。
更好的顺序是：
```
第一批 20–50 条
→ 我们亲自处理
→ 看哪些判断反复出现
→ 形成 semantic rule table
→ 第二批再决定哪些值得自动化
```
也就是：
先人工发现规则，再程序化规则。
不是反过来。
而且我们两个 AI 的优势确实就在这里。
Luna适合：
```
批量读本地数据
整理结构
写转换结果
维护版本
```
我更适合：
```
审语义边界
看不同案例是不是被错误合并
判断这个字段究竟属于 W/O/X/S 哪一层
检查有没有 future leakage
检查规则是不是偷偷根据 A* 定制
```
所以甚至可以做双层：
```
Luna 初标
↓
我抽查 / 争议样本复核
↓
冻结 semantic_v0
```
如果遇到真的模糊的样本，不需要假装确定：
```
uncertain
unknown
multiple plausible interpretations
```
都可以直接保留。
这比一个自动脚本硬输出一个答案科研上更干净。

对，这个我更赞成。脚本做第一遍，AI 做语义 QA，应该会比“全手工”或者“全自动”都稳。
我建议以后固定成两级审核：
- Level 1：脚本自动处理 
  -  切 trajectory 
  -  时间排序 
  -  抽 action / observation 
  -  candidate set 
  -  原字段映射 
  -  provenance 
  -  生成 ReplayRecord 
- Level 2：我/Luna 做 semantic audit 
  -  随机抽样 + 高风险样本全审 
  -  检查 W/O/X/S 归属 
  -  检查 future leakage 
  -  检查 action mapping 是否丢语义 
  -  检查 factual / expanded 有没有混 
  -  检查 LLM-inferred 是否被伪装成 observed 
  -  检查同类事件有没有被映成不同语义 
  -  检查“脚本虽然格式合法，但语义其实错了”的情况 
而且不应该只随机抽 5 条看一眼。第一版 adapter 我建议审得比较重：
前 20–50 条几乎逐条看。
因为这个阶段我们是在验证 adapter 本身。等发现错误模式稳定以后，后续大批量再做：
-  普通样本随机抽查； 
-  异常样本必审； 
-  新 ontology / 新 action type 必审； 
-  低置信度必审； 
-  schema validator 报边界情况必审。 
这样能形成一种很好的循环：
```
脚本转换
→ AI 审核
→ 找系统性错误
→ 改脚本/映射规则
→ 重跑
→ 再审核
→ adapter v1 冻结
```
最重要的是：审核不能只是“看起来合理”。
以后我会专门问这几个问题：
原数据到底说了什么？
 转换后多出了什么？
 少掉了什么？
 哪些是推断？
 这个推断是否依赖未来？
 如果换一个角色/场景，这条规则还能成立吗？
如果某批数据有 1000 条，我们也没必要全人工读完，但可以用“分层抽样”：
```
每种 action type
每种 event type
每种 provenance
最长/最短 trajectory
异常长度
unknown 多的
expanded candidate 多的
LLM-inferred 多的
```
各抽一些。
这样比单纯随机抽样靠谱很多。
所以以后 dataset adapter 的验收我建议直接定成：
“脚本通过 schema”不等于“adapter 通过”。
还必须过一次 semantic audit。
这个完全可以写进仓库规则里。
