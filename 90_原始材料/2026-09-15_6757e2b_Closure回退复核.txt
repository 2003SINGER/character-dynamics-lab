## 1. 最严重：canonical runtime 实际上没有按 `π` 选动作

现在 `ContinuousRuntime::execute_next_boundary()` 在 gate 打开以后：

```cpp
result.decision = decide(...);

for (const CandidateAction& candidate : result.decision.candidates) {
    if (candidate.probability > 0.0) {
        submit_action_intent(candidate.action, ...);
        break;
    }
}
```

也就是：

> **选第一个概率 > 0 的候选。**

不是 sample，也不是 argmax。

偏偏 `Observation` 构造 `A^O` 时：

```cpp
observation.known_actions.push_back(ActionType::Idle);
```

**Idle 永远放第一个。** 

`decide()` 又严格按 `known_actions` 顺序 push candidates，而且 Idle 阈值是 0，因此它基本一定有正概率。

所以现在 canonical runtime 的真实行为很可能是：

```text
DecisionGate opens
↓
π 算了一堆漂亮概率
↓
完全不管概率
↓
第一个 positive candidate = Idle
↓
RunningAction = Idle
```

而旧 Reference 明明是：

```cpp
sample_action(decision, rng)
```

按整个概率分布采样。

这不是小 bug。

这是直接违反我们写进架构里的：

```text
DecisionGate
→ A^O
→ π
→ ActionIntent
```

现在实际上是：

```text
DecisionGate
→ A^O
→ π
→ candidate-list-order
→ ActionIntent
```

### 为什么 17/17 没发现？

因为 vertical smoke 只检查：

```text
decision.candidates 非空
scheduler.running_action 有值
```

**根本没检查新启动的动作是不是 π 应该产生的动作。** 

所以这是验收矩阵的真实漏项。

## 2. 增量数据流还有更隐蔽的 bug：ΔO 没有“消费一次后清掉”

我们一直强调：

> **流动的是 ΔO，不是把历史事件每次重新解释。**

但当前 `execute_next_boundary()`：

```text
advance_next_boundary()
→ apply_world_events()
→ advance_continuous_state()
→ appraise()
→ apply_appraisal_impulse()
```

执行完 `appraise()` 后，我没看到它清：

```text
observation.updates_this_refresh
observation.pending_appraisal_updates
```

也没清已经消费过的 `last_self_action`。

而 `appraise()` 每次都会重新遍历：

```cpp
for (update : observation.updates_this_refresh)
for (update : observation.pending_appraisal_updates)
```

同时只要 `last_self_action.has_action` 仍然为真，就再次解释上次动作。

这意味着可能发生：

```text
09:30 message
ΔO: unread_messages changed
→ X
→ task_pressure +0.08
```

然后 10:00 一个普通 max-step：

```text
没有新 message
但旧 updates_this_refresh 还在
→ 同一条 message 再 X 一次
→ task_pressure 又 +0.08
```

再下一 boundary：

```text
又来一次
```

动作 completion/rejection 也可能类似：

```text
一次 Study completion
→ last_self_action = StudyFocused
→ 每个后续 boundary 都可能再次被 appraise 成
  "task_effort_session"
```

这正好打中了我们这个系统最核心的概念错误：

> **事件不是事件流了，而变成持久驻留、反复触发的输入。**

Reference v0 其实知道这个问题，所以在 appraisal 后会：

```cpp
clear_pending_appraisal_updates(observation);
```



新 canonical runtime 把这一步漏了。

因此 **F / EVENT FLOW 的 exactly-once consumption 现在不能算 PASS。**

## 3. `NeedThresholdCrossed` 会开 gate，但根本不会重新决策

这个也很漂亮地骗过了 acceptance smoke。

代码：

```cpp
if (hunger crossed || bathroom crossed) {
    gate.open = true;
    reasons.push_back(NeedThresholdCrossed);
}
```

很好。

但是后面真正运行 policy 的条件是：

```cpp
if (gate.open
    && (outcome.has_value()
        || !action.has_value()
        || action->status != Running)) {
    decide(...)
}
```



所以：

```text
Sleep 240 min 正在 Running
↓
60min max-step
↓
hunger 穿过 threshold
↓
DecisionGate = OPEN
↓
RunningAction 仍然 Running
↓
条件不满足
↓
不运行 policy
↓
继续睡
```

那这个 `DecisionGate` 开了有啥意义？

我们设计它的初衷明明就是：

```text
NeedThresholdCrossed
→ reconsider current action
→ continue / interrupt / replace
```

现在只是：

> **记录了“我本来应该重新考虑”，然后啥也没做。**

更关键的是 closure acceptance test 只检查：

```cpp
if (reason == NeedThresholdCrossed)
    saw_threshold = true;
```

然后：

```cpp
if (!saw_threshold) fail;
```

它根本没检查：

```text
policy 是否真的运行
RunningAction 是否真的被 reconsider
```



所以 B4/G 被判 PASS，实际上验的只是：

> “有没有写下 NeedThresholdCrossed 这个 enum。”

不是：

> “threshold boundary 是否真的影响行为。”

## 4. 还有一个架构顺序和文档不一致

验收矩阵写的是：

> continuous → completion/invalidation → O → X → S impulse → gate 

但代码实际：

```text
execute_next_boundary()
↓
advance_next_boundary()
    ↓
    scheduler advance
    ↓
    W advance
    ↓
    apply_world_events()  ← O 已经先被改了

回来
↓
advance_continuous_state()
↓
completion
↓
appraise()
```



也就是目前：

```text
W event → O
```

发生在：

```text
S continuous Δt
```

之前。

当前 `advance_continuous_state()` 暂时不读 O，所以数值上可能没炸；但它跟我们固定下来的 runtime ordering **不是同一个东西**。

这至少说明 A2 的“固定顺序 PASS”写早了。

当前至少有 4 个 blocker：

   canonical owner 不能取 first-positive candidate；必须使用明确且可复现的 policy-selection 语义，并测试选择结果真的由 `π` 决定。

4. **boundary ordering 实现与协议不一致**

```text
policy_selection_respects_pi

threshold_gate_causes_reconsideration

```

现有 `runtime_closure_acceptance_smoke` 不够。
