看了这段，也看了仓库现在的 `6cd5a8c`。**SQLite 放弃是对的，但 Luna 最后说“直接 CSV 多路归并”还差一刀，而且当前 PowerWash adapter 有语义问题，不能直接继续全量跑。**

最关键的技术点是：18 张 CSV **不能默认已经各自按 `(pid, Time_utc)` 有序**。官方清洗过程中确实做过排序，但最后是 DuckDB 分表后 `EXPORT DATABASE` 导出，survey 表还经过重新覆盖；不能把“文件当前行序”当研究意义上的时序。因此裸 k-way merge 仍然有风险。

更稳的路线是：

```text
18 张 raw CSV
      ↓ 一次顺序扫描
按 pid hash / pid number 分成 256 个 bucket
      ↓
每个 bucket 独立排序
(pid, Time_utc)
      ↓
按 participant + session 整理
      ↓
Replay projection
      ↓
review fixture
```

这不需要 22GB SQLite 索引，也不需要把 8GB 数据一次装内存。平均一个 bucket 只有全量的约 `1/256`。

而且 PowerWash 当前代码这里我认为**必须先改**：

```python
"source_O": state or None
```

不对。

`CurrentPosition / CurrentJobName / LevelProgressionAmount / CurrentNozzle / IsIdleInGame ...` 是**源 telemetry/game-state 字段**，不能自动等同角色主观 `O`。我们之前给 FarmQuest 定的原则在这里也适用：

```text
telemetry state ≠ O
```

第一版应该：

```python
source_O = None
source_step_context.source_state_fields = {...}
```

以后逐字段审：

```text
CurrentNozzle        → 玩家明确可知？可能
CurrentJobName       → 玩家明确可知？可能
LevelProgression     → UI 是否显示？待核
CurrentPosition      → 引擎知道 ≠ 玩家显式知道
...
```

再决定哪些能进入 O。

另外：

```python
"state_label": event
```

也不合理。`job_completed`、`mood_reported` 是事件类型，不是 Character Dynamics 的 state label。

应该：

```python
state_label = None

source_event.event_name = "job_completed"
```

所以我现在会把 PowerWash 的机制覆盖重新评价成：

| 环节                | PowerWash 实际支持                              |
| ----------------- | ------------------------------------------- |
| 长历史 / `Δt`        | **很强**                                      |
| outcome           | **很强**，task/subtask/job completion、exit 等   |
| source game state | **很强**                                      |
| `W`               | 中等代理，不是完整 authoritative W                   |
| `O`               | **未知/待逐字段审计**，不能直接说强                        |
| `X`               | 无                                           |
| `S`               | 无 ground truth；mood/survey 可作外部 state proxy |
| `P`               | 无                                           |
| `D/U`             | 无直接观测                                       |
| `A*`              | 很弱/基本没有真正 command-level A*                  |

所以它不是“一个数据集覆盖我们大半条机制”。

它真正厉害的是：

> **长时间经历 → 事件/进度/完成 → 主观 proxy 的时间变化**

也就是给 `S` 的 persistence / lag / decay / interruption 这一块提供外部数据压力测试。

LIGHT / ClubFloyd 才更偏动作侧；AGAIN 以后补连续 affect proxy。**几个数据集拼起来覆盖机制，而不是逼 PowerWash 一个人包办。**

你可以直接把下面给 Luna，让它别再试数据库索引方案：

停止继续优化 `powerwash_index.sqlite`。

当前 `6cd5a8c` 的 SQLite 路线废弃。22GB index 暂时保留，等新路线通过 review 后再删除；不要再花时间查询或重建它。

PowerWash 接下来改为：

```text
raw CSV
→ pid bucket partition
→ bucket-local sort
→ participant/session projection
→ review fixture
→ QA
```

## 二、不要裸做 CSV k-way merge

不能假定 18 张 exported CSV 已经分别按：

```text
pid, Time_utc
```

可靠有序。

因此先 partition，再局部 sort。

优先使用 DuckDB 作为**扫描/Parquet 分桶工具**，不是数据库索引。

不要：

```text
CSV
→ SQLite 22GB
→ global ORDER BY
```

改为：

```text
CSV
→ 256 pid buckets
→ Parquet
```

如果 cleaned pid 是：

```text
p1
p2
...
```

则：

```python
bucket = (int(pid[1:]) - 1) % 256
```

不是 `p<number>` 时才使用稳定 crc32/hash。

目标目录例如：

```text
E:\library\科研\PowerWash\partitioned\
  bucket=000\
  bucket=001\
  ...
  bucket=255\
```

允许把 DuckDB temp 放 D 盘：

```text
D:\tmp\powerwash_duckdb\
```

输出仍放 E 盘。

```text
event-specific source fields
```

额外生成稳定：

```text
source_row_key
```

可以基于：

```text
source_file
+
canonical raw row content
```

做 hash。

不要依赖 SQLite rowid。

raw CSV 本身仍是唯一 source of truth。

## 四、每个 bucket 单独排序

对：

```text
bucket=NNN
```

执行：

```text
ORDER BY pid, Time_utc
```

内存只需要处理一个 bucket。

不要再全局排序 3700 万条。

如果 256 bucket 中仍有单 bucket 太大：

```text
256 → 512 / 1024
```

即可，不改语义。

## 五、相同 timestamp 不要伪造因果顺序

当前代码：

```text
ORDER BY pid,time_utc,source_file,row_no
```

虽然 deterministic，但：

```text
source_file alphabetical order
```

不是研究意义上的事件先后。

所以对于完全相同：

```text
pid + Time_utc
```

的事件：

```text
within_timestamp_order = unknown
```

最好形成一个 event bundle：

```json
{
  "t": 123,
  "timestamp": "...",
  "source_O": null,

  "source_event": [
    {...},
    {...}
  ],

  "source_step_context": {
    "within_timestamp_order": "unknown"
  },

  "source_action_A_star": null,
  "W": null,
  "state_label": null
}
```

不要因为 serialization 需要稳定顺序，就把：

```text
source_file A
→ source_file B
```

解释成真实因果顺序。

内部可以按 source_file 排列保证 JSON deterministic，但 metadata 必须明确：

```text
serialization_order_only
```


属于 storage chunk，不是语义 trajectory。

优先按：

```text

→
...
→
```

形成 session。


不要猜。


```text

```

必须与：

```text
semantic/session trajectory
```

分开，不能把 50,000-event chunk 冒充独立 trajectory。
