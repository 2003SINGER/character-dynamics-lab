1. 一条外部轨迹进来之后，到底发生什么

比如 ClubFloyd 某一段真人文字冒险：

O_t:
你站在厨房，桌上有钥匙，门锁着。

历史:
刚才一直在寻找出口。

真人下一步:
take key

第一步不是马上让我们的机制预测，而是 adapter 先把它转成统一记录：

source_O
source_event
A*_t = take key
history
persona?         缺就空
W?               缺就空
candidate_set?   能恢复多少算多少

原始内容始终保留，LLM 推出来的字段单独标 llm_inferred。现在 ReplayRecord 已经支持按字段记录 provenance，所以同一步里真人动作可以是 observed，而推断出来的 W/X 可以是 llm_inferred。

接下来才进入我们自己的场景。

2. 同一条数据要造两个 scene

这是这条路线非常关键的一点。

Factual scene

尽量只包含数据中能证明当时存在的：

room
door
key
...

然后问：

在当时真实可恢复的环境里，我们的机制给真人 A* 多大概率？

这是预测部分。

Expanded diagnostic scene

再人为加入合理但原数据未必明确记录的选择：

window
food
chair
book
phone
leave-room-alternative
...

于是人物不再只有：

take key

一个显然正确的动作。

现在我们可以观察：

take key      0.42
inspect door  0.20
eat food      0.14
sit           0.08
...

如果加入两个无关 object 后 take key 从 0.6 掉到 0.05，那机制很可能根本没抓住“当前目标/承诺/状态”，只是 action space 小的时候碰巧看起来正确。

candidate_set_factual 和 candidate_set_expanded 现在已经在 ReplayRecord 里明确分开，expanded 不允许冒充真人当时真实拥有的候选集。

3. 然后真正跑 Character Dynamics

当前理想链是：

$$ O_t,\Delta O_t,S_t,P \rightarrow X_t \rightarrow U \rightarrow S_{t+1} \rightarrow \pi(A) $$

LLM 最适合插在 X。

比如原始事件：

“角色努力了十分钟，但任务进度几乎没有变化。”

LLM 不应该直接输出：

anxiety += 0.37
task_pressure += 0.21

而应该输出类似：

goal_relevance = high
progress_appraisal = poor
perceived_control = low
frustration_signal = medium
interruption = false

这就是 X。

然后我们的显式动力学：

X + old S + P
↓
U_k
↓
new S

决定：

task_pressure
anxiety
commitment
fatigue
...

怎么更新。

仓库现在已经明确禁止把这一语义层优化掉，也要求以后 LLM 只能读角色合法可知的 O/ΔO/S/P，不能偷看隐藏 W 或未来。

4. “反向纠错”真正纠的是什么

一次 dev run 完以后，我们不会只看：

真人动作预测错没错。

我们还要把整条 trace 展开：

ΔO
↓
X
↓
requested ΔS
↓
applied ΔS
↓
S_t
↓
utility / score
↓
π(A)
↓
A*

然后定位到底哪一层错。

例如真实动作是继续学习，但模型突然跑去睡觉。

可能有完全不同的原因：

X 错了：LLM 把“小进度”理解成重大失败；
updater 错了：一点失败就把 task_pressure 推太高；
decay 错了：fatigue 长时间不恢复；
state 定义错了：anxiety 和 task_pressure 实际高度重复；
decision coupling 错了：fatigue 对睡觉 utility 权重过大；
action support 错了：真实环境里其实根本不能睡；
当前数据根本不支持我们假设的那个 state。

所以“预测错”不是直接改权重。

而是：

先找错误发生在哪个计算边界。

这也是为什么中间链不能被 LLM 黑盒化。

5. 接着做 sensitivity，而不是凭感觉改

比如怀疑 fatigue 太强。

固定同一时刻其他变量：

$$ fatigue = 0.2,\;0.4,\;0.6,\;0.8 $$

看：

$$ \pi(A) $$

怎么变化。

如果从 0.2 到 0.8：

SleepAtBed 几乎完全不变

那有几种可能：

fatigue 根本没接进 decision；
权重太小；
被别的变量压死；
或者这个字段就是没用。

如果一从：

0.49 → 0.51

就让睡觉概率：

0.1 → 0.8

那就是响应曲线过陡。

再做 ablation：

full model
vs
remove fatigue

如果预测和 expanded diagnostic 都不受影响，

删。

不是说：

“fatigue 在心理学上应该存在，所以保留。”

6. 不只是调参数，还允许改“结构”

这才是这条路线最有意思的部分。

循环里允许改变的不只有：

α = 0.2 → 0.3

还可以是：

删除字段
合并字段
改变 updater 形式
新增 lag
加入 decay
把线性函数改成阈值/饱和函数
改变 X→S coupling
改变 S→π coupling
删除已经被 LLM semantic layer 替代的手写语义 rule

比如一开始我们有：

task_pressure
anxiety
frustration

跑几个 dev 数据集之后发现：

frustration 和 anxiety 高度共线
删 frustration 没损失

那最终机制就变成两个字段。

甚至可能最后只剩：

fatigue
goal/commitment
affective pressure

三个真正有用的 persistent dimensions。

这反而是成功。

我们的目标不是把 Character Dynamics 做得越来越大，而是让外部数据把它削成一个比较小、但行为上真的有作用的系统。

7. 不同数据集负责纠不同部分

这也是为什么我们前面要找多种数据。

ClubFloyd 更适合纠：

O / semantic X / action choice

因为有：

文字情境 → 真人 action

AGAIN 更适合纠：

X → affect-like S
lag
decay
saturation

因为它有连续 arousal proxy。

PowerWash 更适合纠：

长时间尺度 S
跨 session persistence
progress / interruption / enjoyment / competence

LIGHT 更适合纠：

world/object/action
affordance
角色环境中的 action competition

所以不是每个数据集都必须拥有完整：

$$ W,O,X,S,P,A $$

它们分别给不同边施压。

8. 一个完整 dev iteration 长什么样

真正执行时，可以压成这一轮：

取一批 dev trajectories；
adapter 转 ReplayRecord；
构建 factual + expanded scenes；
LLM 生成结构化 semantic X；
当前 mechanism v0 跑完整 trace；
计算真实 A* 的 NLL/rank，并看 expanded-scene robustness；
对 S 字段和参数做 sensitivity / ablation / permutation；
LLM + 我们阅读 failure traces，提出机制解释；
只改有证据支持的部分；
在同一 dev 或另一个 dev split 重跑；
反复几轮后，开始删掉无效机制；
最终冻结成 v1。

这时候“LLM + 我们诊断”不是让 LLM直接说：

“把 anxiety 改成 0.38。”

而是让它帮助提出：

“可能是 task_pressure 和 anxiety 重复。”

“可能是 updater 无衰减。”

“可能是 X 把轻微失败映射得太严重。”

然后我们用实验验证。

9. 什么时候停止继续调

这个也很重要。

不能永远：

测试
→ 不爽
→ 改一点
→ 再测试

否则永远是过拟合。

所以最终要到一个时间点：

S fields frozen
X schema frozen
U frozen
utility form frozen
parameters frozen
timing frozen

得到：

Character Dynamics v1

从此新 test dataset 只能前向跑。

仓库现在已经明确这一点：任何参与字段、updater、utility、timing、ontology 保留/删除决策的数据都自动属于 dev；机制 freeze 后 test 不能反向参与修改。

10. 最后才是真正厉害的部分：新数据来了

比如我们此前从没碰过一个新游戏日志数据集。

这时同时跑：

A. Frozen v1 + fixed/rule semantics

B. Frozen v1 + live LLM semantic X

C. LLM direct
   O + history + P → action
   不用我们的 S

D. v1 - S / permuted S

E. literature baselines

如果结果：

$$ B > C $$

并且这种优势在多个新域都存在，

那说明：

通用 LLM 负责理解新语义，而显式 persistent dynamics 真的贡献了 LLM 单独读 history 没得到的东西。

如果：

$$ B\approx C $$

那我们就得接受：

这套显式 dynamics 在该任务里没什么额外价值。

如果甚至：

$$ C>B $$

那更说明机制结构可能在妨碍模型。

这才是整个项目最终有研究价值的地方。

那我们就能很干净地问：

LLM 是否真的能替代我们花很多轮人工得到的语义映射？

如果：

$$ B \approx A $$

那很好。

说明：

这个 semantic task 确实是 LLM 很擅长、一次提示就能完成的。

我们可以删掉大量手工语义规则。

如果：

$$ B < A $$

就能看错在哪里，再改 prompt/schema。

如果：

$$ B > A $$

也很好，说明我们的人工 rule 太僵，LLM 提供了真实的跨语境能力。

甚至可以进一步测“提示词是不是我们从 loop 里学出来的”

比如：

LLM naive prompt

vs

LLM prompt informed by mechanism-identification loop

如果后者明显好，

那说明前面的 rule engineering 没白做：

它帮我们识别出了 semantic interface 真正需要哪些判断。

这虽然可能不是主论文 claim，但非常有分析价值。

复杂的显式语义规则不需要长期保留；LLM 足以承担语义映射，而真正需要显式建模的是跨时间 dynamics。

这反而可能把最终系统削得更漂亮。
