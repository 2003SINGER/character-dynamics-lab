## 最严重的一个真 bug：runtime rejection 其实没进入 O

现在：

```cpp
ContinuousRuntime::submit_action_intent(...)
{
    WorldOutcome validation = world_runtime_.validate_runtime_start(...);

    if (!validation.accepted) {
        scheduler_.reject_action(...);
        apply_self_action_feedback(observation_, validation, ...);
        return validation;
    }
}
```

看起来对。

但是 `validate_runtime_start()` 创建的 `WorldOutcome` **没有设置 `provenance`**。

而：

```cpp
apply_self_action_feedback(...)
{
    if (outcome.provenance.empty()) {
        observation.last_self_action = {};
        return;
    }
```

直接返回。

所以：

```text
ResourceInsufficient
TargetAbsent
TargetUnusable
PreconditionFailed
```

经过新的 canonical `submit_action_intent()` 拒绝时：

```text
W reject
↓
scheduler 安排 1min rejection marker
↓
apply_self_action_feedback()
↓
因为 provenance 为空
↓
直接 return
↓
ActionConstraintBelief 根本没写
```

也就是说我们前面已经修好的 **Typed Rejection Feedback v0，在新 Continuous Runtime 路径里还没真正接通。**

这是 **E1/E2 HARD FAIL**。

而且 scheduler 那边还是：

```text
"action_rejected:" + action + target
```

字符串 marker，不带 typed `WorldOutcome` payload。

所以现在正好是我们验收标准禁止的：

```text
typed outcome 一套
+
scheduler string rejection 一套
```

还没统一。

## 第二个真 bug：Deadline 虽然“加进 next event”了，但查询顺序是错的

这次它确实把 task deadline 加进了 `next_runtime_event_after()`。

但代码是：

```cpp
for day:
    for scheduled_event:
        if event > now:
            return scheduled_event;

    for task:
        if deadline > now:
            return deadline;
```



注意：它不是求所有候选的：

```text
min(timestamp)
```

而是**先找到任何一个未来 scheduled event 就 return 了**。

例如：

```text
now       = 09:20
deadline  = 09:25
message   = 09:30
```

函数会：

```text
先遍历 scheduled events
→ 找到 09:30 message
→ return 09:30
```

根本看不到下面的：

```text
09:25 deadline
```

然后 W 从 09:20 一口推进到 09:30 时，`advance_runtime_by()` 虽然会发现：

```text
task-deadline occurred_at = 09:25
```

但角色已经 **09:30 才处理它**。

这正是我们 Closure B3 要防的：

> event 虽然存在，但没有成为正确 runtime boundary。

所以目前：

**Deadline 仍然不能迁。**

---

## 第三个 bug：World boundary 自动续订会重复注册同一个未来事件

现在每次：

```cpp
advance_next_boundary()
{
    ...
    schedule_next_world_boundary();
}
```



但 scheduler 的：

```cpp
schedule(...)
{
    scheduled_events_.push_back(...)
}
```

**没有 dedupe。** 

比如：

```text
RunningAction completion = 09:30
next WorldEvent          = 11:00
```

已有一个 11:00 W boundary。

09:30 action completion 后：

```text
advance_next_boundary()
→ 再 query next WorldEvent
→ 还是 11:00
→ 又 push 一个 11:00
```

现在两个。

如果中间又因为 max-step 出现 10:30 boundary：

```text
→ 又 schedule 一次 11:00
```

变三个。

到 11:00 scheduler 会一次拿到一堆重复的 boundary marker。

World 本身只产生一个真实 event，所以暂时可能没炸行为，但：

> **boundary ownership contract 还是错的。**

而且刚加入的 60min max-step 会让这个重复注册更容易出现。
