---

但我继续往下看，现在真正该修的不是 Deadline，而是 **Action 生命周期 + canonical dataflow owner**。

最严重的是这个：

## 现在没有 start validation

当前还是：

```cpp
scheduler.start_action(...)
```

直接生成 `RunningAction`。

`RuntimeScheduler::start_action()` 完全不问 W：

```text
ActionIntent
→ 直接 Running
```



然后过了比如 35 分钟，才调用：

```cpp
world.settle_runtime_completion(...)
```

而这个函数内部又重新：

```cpp
if (!can_execute(plan.action)) reject;
```



于是理论上现在可以：

```text
09:00
角色选择一个实际上非法的动作

↓ 没有 W validation

09:00–09:35
RunningAction 正常跑了 35 分钟
S 也按“正在执行这个动作”演化了

09:35
W 才说：
“不行，这动作其实不能做”
```

这肯定不对。

正确生命周期必须变成：

```text
π
↓
ActionIntent
↓
W.validate_start()
      │
 ┌────┴─────┐
 │          │
reject    accept
 │          │
Outcome   RunningAction
 │          │
O/X/S      时间推进
```

然后 **completion settlement 不应该再承担“这个动作一开始是否合法”的职责**。

如果中间 W 条件变化让动作不能继续，那是：

```text
RunningAction
→ PlanInvalidated / PhysicalPreemption
→ typed outcome
```

而不是完成时突然重新审判开始条件。

这个是当前第一优先级。

---

第二个问题也很关键：

## WorldEvent 仍然不知道怎么自动成为 scheduler boundary

现在 smoke 是：

```cpp
scheduler.schedule({
    "world_event_boundary",
    09:30,
    false,
    false
});
```

然后到了 09:30，`World::advance_runtime_by()` 才真的产生 `message-study-group`。

这比以前“手工制造 message”已经好很多。

但问题是：

> **谁告诉 scheduler 09:30 有世界事件？**

还是测试代码自己。

也就是说现在是：

```text
测试作者：
“我知道 W 09:30 有消息，所以请 scheduler 09:30 停一下。”

scheduler → 09:30

World：
“对，我这里确实产生了消息。”
```

真正 runtime 应该反过来：

```text
World/EventSource:
next event = 09:30

RunningAction:
completion = 09:55

State:
next threshold = 09:47

Scheduler:
min(09:30,09:47,09:55)
= 09:30
```

所以最终 boundary sources 应该真正汇总：

```text
next world event
next action completion
next state threshold
external input
hard preemption
```

而不是 fixture 手工 schedule 世界本来自己已经知道的事件。

否则随机世界事件依然没有真正接进时间骨架。

换句话说：

所以我们真正的数据流还差这一段。

还有两个次一级问题也已经冒头了。

`settle_runtime_completion()` 当前明确让：

```text
completion.elapsed_minutes == 0
```

测试甚至把它写成 invariant。

从“该函数不负责推进时间”角度这没错，但从 `WorldOutcome` provenance 看会很歧义：

> 一个持续 35 分钟并成功完成的动作，outcome 却写 elapsed=0。

以后最好区分：

```text
time_advanced_by_settlement = 0
```

和：

```text
action_elapsed_minutes = 35
```

否则 trace 会误导 evaluator。

而且 runtime study settlement 现在：

```cpp
action_elapsed =
    action_definition(action).default_duration_minutes;
```



所以假设未来：

```text
RunningAction StudyFocused
planned_duration = 50min
```

完成后 W 还是按默认 35min 算 effort。

这说明 `WorldOutcome` / completion settlement 最终应该吃真正的 RunningAction completion context，而不是重新从 `ActionType` 猜时长。
