这个loop怎么设计？













不是给 shop_on_phone 单独打一块补丁。这个地方应该设计成一个通用的“失败动作反馈闭环”，正好补全我们原来的：
O → A^O → π → action → W settlement → feedback → O
现在缺的就是最后这半圈。
我会把它设计成：
O / S
  ↓
生成 A^O
  ↓
π(A)
  ↓
选择 action + target
  ↓
W 检查真实 precondition
  ↓
┌──────── accepted ────────┐
│                          │
│ 正常 settlement          │
│ 时间推进 / W 改变         │
│                          ↓
│                     action outcome
│                          │
└──────────────────────────┤
                           ↓
                    actor-local feedback
                           ↓
                    更新 O / ΔO
                           ↓
                    下一轮重新生成 A^O
重点是 rejected 分支：
W rejects action
      ↓
typed rejection reason
      ↓
转化成“角色合法获得的新知识”
      ↓
写入 O
      ↓
A^O 下一轮改变
1. W 只负责说“为什么失败”
这个其实现在已经有雏形：
enum class RejectionReason {
    TargetAbsent,
    TargetUnusable,
    ResourceInsufficient,
    PreconditionFailed
};
这层很好。
W 不应该直接改 O，也不应该说：
wallet = 13

如果角色实际上没有办法知道精确余额。
它只提供交互真实结果：
action = shop_on_phone
target = phone
accepted = false
reason = ResourceInsufficient
2. O 根据失败原因形成“最小必要知识”
这里才是我们现在缺的。
最简单但我不太推荐的是：
shop_on_phone_available = false
因为太 action-specific。
更好的结构可以叫：
struct ActionConstraintBelief {
    ActionType action;
    std::string target_id;

    ConstraintType constraint;
    bool satisfied;

    std::string source;
    int observed_at;
};
例如这次：
action = shop_on_phone
target = phone
constraint = ResourceRequirement
satisfied = false
source = failed_direct_interaction
O 就知道：
“我现在不能完成这个购物动作，因为资源条件不满足。”

但不需要知道真实 W.wallet。
这很符合我们的 W != O。
3. 下一轮 A^O 用这个知识过滤
现在逻辑大概是：
if O knows wallet:
    wallet >= 30
else:
    allow ShopOnPhone
以后变成：
known explicit blocker?
    yes → 不进入当前可执行 A^O
    no  → 再检查 O 中已知普通 precondition
于是：
第 t 轮

O:
    没有 wallet 知识

A^O:
    shop_on_phone ✓

→ 尝试购物

W:
    ResourceInsufficient


第 t+1 轮

O:
    action.shop_on_phone:
        ResourceRequirement = unsatisfied

A^O:
    shop_on_phone ✗
loop 当场断掉。
但是最关键的是：怎么恢复？
不能：
失败一次
→ shop_on_phone 永久封印
那一样是错的。
所以每一个这种 blocker 都必须有一个失效条件。
比如：
ResourceInsufficient blocker
    ↓
如果角色后来观察到 wallet 发生变化
    ↓
blocker 失效
    ↓
重新根据新的 O 判断 shop_on_phone
例如：
10:00
购物失败
→ ResourceRequirement unsatisfied

12:00
角色收到 100 元
→ O.wallet changed
→ invalidate resource blocker

12:01
A^O 重新包含 shop_on_phone
因此完整闭环其实是：
尝试
 ↓
失败
 ↓
获得失败知识
 ↓
暂时阻止重复尝试
 ↓
相关条件发生变化
 ↓
旧失败知识失效
 ↓
动作重新开放
这才叫 recoverable。
四种 rejection 可以分别怎么处理
我觉得直接形成一张映射就很好：
W rejection	O 学到什么	什么时候恢复
TargetAbsent	目标当前不存在	再次发现目标
TargetUnusable	目标当前不可用	观察到 usable 状态变化
ResourceInsufficient	某资源条件当前不满足	相关资源发生可信更新
PreconditionFailed	某前置条件当前不满足	对应 precondition 的 O 更新


你会发现，Phone fixture 已经实现了第一行。
所以我们现在不是新造一个机制。
是在把：
TargetAbsent
→ O correction
推广成：
typed W rejection
→ typed epistemic correction
这其实很漂亮。
还有一个容易踩的坑
不要让：
rejected action → S 直接变化
比如：
购物失败 → anxiety +0.2
这个不应该写死在反馈层。
正确的是：
W rejection
↓
O 得到：
resource requirement unsatisfied
↓
ΔO
↓
X 解释：
“想买东西但钱不够”
↓
S 是否焦虑、失望、烦躁
由 X + P + 当前 S 决定
所以严格保持：
W
↓
typed outcome
↓
O
↓
X
↓
S
↓
π
千万别 W outcome → S 抄近路。
至于 elapsed_minutes = 0，我反而暂时不会急着改。
失败动作到底耗不耗时间，是另一件事。
比如：
- 点付款发现余额不足：可能耗 1 分钟；
- 拉门发现门不在：几秒；
- 尝试启动坏掉的电脑：可能 2 分钟。
未来可以让 rejection outcome 自己有：
attempt_duration_minutes
但这只是模拟精度。
这次 loop 真正的问题不是 0 分钟，而是失败没有产生新的决策信息。
我会先把这个机制叫：
Typed Rejection Feedback
它刚好可以成为 W → O 的一个正式接口。这样这个 bug 修完，不只是“购物不循环了”，而是整个 Character Dynamics 多出一块非常合理的通用机制。
