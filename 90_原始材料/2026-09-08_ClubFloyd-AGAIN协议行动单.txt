现在进入 ClubFloyd 主线。

主任务：ClubFloyd Source-Command Development Protocol v0

目标不是马上训练 Theory-S，而是冻结一个最小、可执行、不会因开放文本 action 而偷换任务的 next-action development protocol。

母问题保持：

H_obs_<t → persistent S_t → next player action A*_t

不要修改 Theory-S。

1. 先冻结 usable action subset

基于现有：

425 trajectories
438,188 steps
command-like 218,575
ambiguous 219,524
chat/commentary-like 47
meta-command 42

不要立刻大规模人工标注 438k。

从现有 review fixture 开始，审计：

command-like 规则 precision；
ambiguous 中主要有哪些类型；
chat/meta 是否可稳定机械排除；
[STATE] → [ACTION] 是否确实保持 player-command boundary。

输出一个冻结规则：

verified_command_like_v0

允许：

deterministic rule；
少量 Terra semantic classifier；
但必须版本化、gold/source provenance 清楚。

Terra 只能分类 action 本身是否是可评玩家 command，不能看未来 state。

2. 不要求第一版先有 finite candidate set

这一点非常重要。

ClubFloyd 是开放文本 command。

第一版协议不要为了兼容旧 NLL harness，强行把它改造成伪 finite A^O。

先明确区分两个阶段：

Stage A：source-command prediction/evaluation

研究：

history/state representation → observed next command

Stage B：finite candidate-set reconstruction

只有 Stage A 证明值得继续后再做。

不要因为 source 没 candidate set 就阻塞 Stage A。

3. 冻结开放文本 action 的 canonicalization

需要定义一个最小 command representation，例如：

verb + target + optional modifier

例：

take lamp
open wooden door
go north
ask bartender about key

但不要提前假定所有游戏命令都能完美解析。

输出：

exact raw command；
normalized command；
parse confidence；
verb；
target；
modifier；
parse status。

原始 command 永远保留，不可被 canonical form 覆盖。

4. 冻结第一版评价指标

因为现在不是 finite candidate set，所以不能硬套 candidate-set NLL。

第一版只需要设计一个公平的 development evaluation。

至少比较：

exact normalized-command accuracy；
verb accuracy；
target accuracy；
semantic command match；
optional top-k retrieval/ranking if a frozen candidate pool can be constructed without gold leakage。

其中 semantic match 必须使用冻结 evaluator，不能边看结果边改规则。

如果不能定义可靠概率空间，就明确说：

ClubFloyd Stage A 暂不提供 canonical candidate-set NLL。

这是允许的。

5. 冻结 history boundary

输入只能包括：

current pre-action [STATE]_t
previous source states/actions
same transcript history

禁止：

current A*_t
next [STATE]
future command
从 post-action text 反推 current action

检查 parser 是否存在 off-by-one。

6. 冻结 trajectory split

按完整 transcript / game trajectory 切分。

不能 step-level random split。

要求：

train
validation
development holdout

trajectory-disjoint。

如果能识别 game/domain，还应记录是否存在同游戏跨 split；这轮先报告，不要为了追求 cross-game generalization 过度设计。

7. 只做一个小 protocol fixture

先选一个 deterministic 小切片，例如：

20–30 trajectories
或
1,000–3,000 verified command-like steps

目的只是验证：

parser
history boundary
command canonicalization
evaluation
split

不要开始 Theory-S 参数训练。
