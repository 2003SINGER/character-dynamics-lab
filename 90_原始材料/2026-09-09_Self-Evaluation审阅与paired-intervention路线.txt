问题是：现在别真的把这些 score 冻死。
现在几个分数其实还不能按表面理解
最搞笑的是：
BehavioralDiversity = 0.0566
看起来低得一批。
但代码定义是：
unique actions / 256
我们一共就 16 个动作。
所以理论最大值：
\[
16/256=0.0625
\]而：
\[
0.0566\times256\approx14.5
\]也就是说实际平均一个 run 已经用了大约：
14.5 / 16 种动作

所以这个所谓 0.0566 实际上接近它自己定义下的满分。
指标尺度写歪了。
另一个：
WorldValidity = 1.0000
代码其实是：
float(row['accepted']) in (0.0, 1.0)
这只证明：
accepted 这一列里面写的是合法的 0/1。

它根本没证明：
世界运行有效。

甚至某个 action 被 W 合理拒绝，accepted=0，这个检查照样记 1。
所以现在这个应该叫：
TrajectorySchemaValidity

或者 AcceptedFieldValidity
而真正的 WorldValidity 应该检查：
动作是否合法结算
primitive invariant
状态值域
世界状态一致性
资源是否越界
task progression 是否逆行
unsupported action 是否执行
...
这个以后可以直接利用现有 verify() / W invariant。
然后：
CausalResponsiveness = 0.9301
Adaptivity          = 0.9301
完全是同一个指标。
都是：
出现 event 后，下一步 chosen action 跟上一步不一样了吗？

这甚至目前连 responsiveness 都很难叫。
因为一个本来就高度随机、每步经常换动作的 NPC，也能轻松 0.93。
真正要测的是：
\[
\Delta\pi =
D(\pi_{\text{intervention}},
  \pi_{\text{control}})
\]而不是：
action_t != action_t-1
所以你们 scenario manifest 里写的：
hidden_phone_removed
visible_phone_removed
task_deadline_shift
才是正路。
还有：
Persistence = Commitment = 0.9795
也是同一个指标重复放两个名字。
这版没关系，但以后必须拆：
- Commitment continuity：一个 intention 是否保持；
- State persistence：某次事件造成的 ΔS 是否跨多步残留；
- Behavioral persistence：对应的 π(A) effect 是否跨多步仍然存在。
这三个完全不是一回事。
Efficiency=0.0 也有同样的表示问题。
实际意思是：
0 LLM calls

这当然是现在 rule-only runtime 的优点。
但写成 score=0 看起来像效率最差。
我建议 Efficiency 根本先别归一化成 score，直接保持：
model_calls / decision
tokens / decision
P50 latency
P95 latency
GPU ms / decision
CPU ms / decision
memory
以后做 Pareto comparison。
