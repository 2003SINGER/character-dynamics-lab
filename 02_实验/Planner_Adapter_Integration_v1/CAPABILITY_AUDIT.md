## Can an existing bound actor task be a lawful subtask without dispatch?

**Native Note lifecycle correction (2026-10-12):** P5 reset does not create a Note in A's inventory. The saved native minute-0 snapshot has no Note location and neither actor holds one. `p3/p4_social.py::_request_note` (180–214) first asks the native social client, then on a supported request creates the physical Note directly at the recipient. Consequently “A already holds Note” is not an author requirement or native request precondition. The adapter initially imposed that condition incorrectly; its blocked replay is retained in `validation/real-source-runs/real-source-snapshot-replay-20261012T024528Z-96e72d/`. The correct forecast is conditional native request → generated recipient-held Note → actual response; creation and response are still not guaranteed or author-dispatchable. Known A/B inventory ownership is a representable W state, not an unregistered room.

Yes, narrowly, in principle: A and B already own fixed `deliver_supply` bindings at reset, and their GTPyhop callbacks pursue those local goals without a controller assigning a new task. A high-level planner can represent “await A's native delivery receipt” as a condition, leave that goal to the actor's own planner, then recompute the remaining candidate from the sealed ledger. That would be a condition/wait handoff, not a new assignment or accepted task.

That loop is not currently implemented by the route-only Sabre adapter. It only emits a route-open proposal; its projection marks non-route hard constraints residual, and it has no candidate/action for waiting on a named receipt or for a delivery failure. P5's own Director independently recognizes delivery prerequisites and actors independently run GTPyhop, so seeing all three in one trace would still not prove a causal cross-planner handoff. A future integration needs explicit mapping from each authored obligation to the existing actor binding, a wait condition keyed to the receipt-backed event, and evidence that receipt / failed / unavailable updates change the next high-level candidate. Do not label it dynamic dispatch.

## Time model: what can be derived, and what remains uncertain

Do not use prior run completion times (e.g. 6 or 16 minutes) as constants. The source provides these modelable quantities:

1. **World clock:** each `step_world` round advances by `p4_clock.step_minutes` (P5 initializes it to one minute); no action itself advances time (`p4_world.py:104-121`, `p5/service.py:486-497,596-624`).
2. **Actor primitive cadence:** if no pending action exists, `step_actor` asks GTPyhop and records a `planned` pending action; on the next callback it dispatches that pending action and returns (`p5/agency.py:27-38,53-138`). Thus a first primitive needs a planning callback followed by a later dispatch callback; following primitives are likewise planned after the prior dispatch. For a fully known route with no interruption, a primitive-count lower bound is `2 × (shortest-path move edges to item + GET + shortest-path move edges item→destination + DROP)` simulated minutes from a clean t=0, assuming each callback consumes one configured minute. This is an adapter-derived lower bound, not a promise; route discovery, unavailable actions, social work, pauses, player interference and failure add time.
3. **Topology and resource cost:** compute directed shortest paths from the actual generated exits and each actor's local known/traversable graph; native route costs and opportunity count are checked against the active bundle and physical budget (`p5/world.py:88-112,115-183`). Unknown local edges must not be treated as known by the actor. The current route `min_minutes` 2/3 is registered separately and is not a complete task schedule.
4. **Social time/outcome:** note request requires A's settled delivery and visible co-location; B's actual response is an Ensemble action at B's callback (`p4_social.py:430-465`). Source has no deterministic response-time bound or guaranteed outcome. Represent this as conditional/uncertain and use the native response ledger for completion, not a fixed duration.

The formula above is only an execution lower bound after a path is known locally, not a whole-task ETA. The successful matched side-route native trace shows A makes three exploratory moves (south→east→south), returns north to pickup, then gets, moves south/east, and drops. Each intent is dispatched on a later callback; drop settles at minute 16. Thus the two-edge pickup→destination path alone materially understates elapsed time when local route discovery is needed. The exact evidence is `02_实验/System_Baseline_v0/runs/C1-C2-side-C3-reject-20261011T164643Z-5b5c12/steps/minute-01.json` through `minute-16.json` plus `native_final_trace.json` (trace SHA-256 `77d8f1a6d35e037b2b3b6982df0d984cb5d5050abea55970790b84cfb55a0869`). For future timing estimates, include the local-observation/discovery policy and callback sequence; when they are not predictable from current observation, report a conditional lower bound plus unresolved overhead, not a fixed ETA.

Useful prior pattern (not a P5 capability claim): `tools/planner_p0_v0/integration_v0/sabre_export.py:28-69,151-185` computes a finite delivery macro's move/get/drop primitive-count forecast from observed topology and actor-local item knowledge, then models it as a Sabre compound action; it labels the cost a forecast, separate from P3 GTPyhop refinement/native settlement. P5 can reuse the derivation idea, but must account for its callback cadence and local information, not copy that P0 domain's timings.

## M1 audit outcome and implementation implications

- **Confirmed reusable:** Sabre v0.8's native causal/action/author-utility/character-utility/consent/belief machinery; GTPyhop's actor-local HTN decomposition of the already-bound delivery goal; P5's result-to-prerequisite mapping, native permissioned route action, receipt-backed drop and social ledgers, and sealed-prefix feedback.
- **Current mismatch:** the P5 Sabre domain is only two route opportunities selected in response to an explicit route-open goal. The more meaningful “delivery → possible note request → actual response” dependencies are present in P5 Director and event ledgers but not represented as Sabre actions/conditions, nor handed off to actor tasks by the external planner.
- **No dynamic task dispatch:** this is a real P5 capability absence, but not an automatic reason to stop. First try a condition/wait handoff to existing bound A/B goals; dispatch is only needed if the chosen task is not already bound.
- **Cannot promise:** that a proposed actor plan executes, an NPC accepts/continues, the note is answered, or an answer arrives by a chosen time. Sabre's simulated consenting-character plan is an explanatory candidate; P5 GTPyhop/Ensemble and Evennia remain the actual decision/settlement chain.
- **Audit limit:** this establishes API/domain expressiveness and current wiring from source, not A1–A8 behavior or end-to-end success. Those require traceable real Sabre calls, GTPyhop calls, native receipts and a matched P5 Director comparison.
