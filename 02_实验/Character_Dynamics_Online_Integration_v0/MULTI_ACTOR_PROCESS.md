# Multi-Actor Process — 营地巡察、交接与集结

**状态：DEVELOPMENT / PARTIAL / READY_FOR_INDEPENDENT_REVIEW。** 2026-10-19 授权的多角色持续过程已完成一次有界原生运行，但未完成两处集结与全部作者义务；本轮停止扩展并提交独立审阅，完整过程未通过。真实结果见 [MULTI_ACTOR_RESULTS.md](MULTI_ACTOR_RESULTS.md)。本计划仍定义同一在线 Controller 的目标边界，不代表完整系统已实现。

## 目标

让同一持续运行世界中的至少两名 Character Dynamics 角色各有可追踪的自身目标和跨时间计划；作者可加入、并行维护和编辑由状态/事件/顺序/期限构成的未来要求；协调过程能在共享因果变化或作者编辑后组织并局部修复受影响的后续计划。真实执行结果由游戏执行器结算；已结算历史、合法 inflight 动作和未受影响计划不得被重置或假取消。角色未被作者规定的行动空间留给系统组织。

本里程碑不是“再跑一次招募”，也不把单独验证“结算后 edit”或修复正常关机作为主里程碑；这些边界测试与工程维护服务于同一多角色过程。不得把 one-step RecruitMember 继续包装成持续多步规划。应复用成熟规划方法，不新造通用搜索内核、第二套 Controller/历史系统或独立示例程序。科研记录随实现推进：成熟基线解决了什么、模型与游戏内容怎样建立、人工建模劳动、角色计划冲突/修复和真实运行代价，以及哪些问题仍无证据。

## 游戏内容与 G1 边界

本次授权允许为选定过程开发明确版本化的 G1 游戏内容。每项新增能力必须与原生 G0 分开标明，并有完整前提、效果、失败条件和可实际执行/结算的规则；不能用 Planner 的预期效果伪装成游戏状态，也不能把 G1 结果报告成原版 Veloren 能力。G0 仍按既有规则处理。

首个过程选择为**营地巡察交接与队伍集结**：头目与巡察员各有自身任务；巡察员在两个 G1 营地地标间选择巡察/交付顺序，头目依据实际收到的到访记录选择招募和集结方案，已有原生 NPC 接受或拒绝招聘并自行跟随。没有把原生海盗 raid 的占位活动当成真实袭击/战利品能力。NPC 身份在同一既有世界中核实，不另造测试世界。

| 能力 | 来源与执行边界 |
|---|---|
| 走到目标、交谈、避险及原生行为恢复 | 复用 G0 Brain / Controller / Agent；不传送、改坐标或替换整个 Agent |
| 招募、受雇与跟随 | 沿用已验证原生 RecruitMember / RequestHire / Hired / Following；不放宽原生职业、人口和世界前提 |
| 巡察到访记录 | **G1 `recon-v1` 新内容**：实际到达注册地标并连续驻留至少 2 个原生 Time 秒，才由游戏结算本人记录；不是“道路安全”或“袭击成功”的证据 |
| 向另一 NPC 交付记录 | **G1 新内容**：本人有记录、双方距离合法且原生交谈实际执行后，接收者才获得 G1 知识；不以请求接受或 Planner 预测写知识 |
| 队伍集结 | **G1 新内容**：头目已经收到相关记录、有真实受雇随从，且两者实际到达地标才结算；移动和跟随仍由原生执行 |

两名角色各持跨时间目标、HTN 计划节点、真实执行进度与合法观察；Director 使用同一个协调状态，而不是每种动作再建控制器。完成节点由权威回执推进；未完成前的预测效果只在规划器中存在。作者可并行提出状态、事件先后和绝对期限要求，并在独立控制周期编辑尚未结算的未来；不得用全局监测事实冒充角色观察。

持续运行应包含：无作者输入时两名角色已行动；至少一项真实结算后加入作者要求；下一独立周期编辑未来约束；按依赖保留已结算前缀、无关计划与合法 inflight，修复受影响的后续节点；最后继续原生/角色过程。动作顺序由目标、观察、HTN 方法和执行反馈产生，不将运行器的场景输入编成完整动作序列。计划协调、未知/冲突及执行失败按实际记录，不预设成功。

正常关闭的既有问题已定位：旧配置的 SIGUSR1 更新关闭宽限为 120 秒，而旧监督器约 16 秒即发 SIGTERM。新独立配置可显式设为 5 秒，并等待原生关闭及落盘；不改写旧运行、不把修复当本工作包主目标。新 G1 二进制、配置和规则版本须另行固定，原 G0 二进制及旧输入保持原样。

实现与离线回归通过后，由主级固定运行输入再启动。单次持续开发运行最多 720 秒、最多 30 项真实请求、20,000 条记录与 64 MiB 输出，保留至少 6 GiB 可用磁盘；允许先做不超过 60 秒的接口预检，独立保存，不冒充正式过程。失败不通过换世界或放宽规则抹去。架构需能向更多角色、并行义务及更丰富作者语义生长，但本轮不要求所有 NPC 自主规划、任意自然语言、无限分支或通用剧情系统。

## 固定开发实例

复用原始 Source-A 世界副本中的头目 476 与巡察员 433，另选同一世界中实际符合原生招募条件的非会话 NPC 为随从；禁止将独立巡察员招为随从。两处 G1 地标均支持巡察与集结，导航代价依据角色自身位置及注册地标估计。巡察员需完成两处巡察并交付记录，顺序不由运行器预写；头目需招募随从，并根据巡察员实际交付的记录选择集结地点。

第一次真实巡察结算后，由明确标为 `RUNNER_DEMO` 的输入生产器在三个独立决策周期分别加入交接状态及事件先后要求、加入 A 地标集结的绝对期限，再将未来集结目标编辑为 B。绝对期限固定为首次巡察结算时间加 240 个原生 Time 秒，不因编辑重置。这是程序化作者编辑开发验证，不是已完成的人工交互评价。

传统协调器采用固定优先级的逐目标 HTN 细化，每名角色最多一项在途请求；它不是全局最优的多主体联合搜索。作者事件顺序约束必须约束实际派发，不能只在事后监测。预测的事件效果用于规划，真实事件见证只来自相关联的原生终态。G1 报告知识的含义限于原生实际发声后发生的版本化交接，不等同于完整社会理解或原版 NPC 自主接受。
