## Loaded Msg dispatch boundary

In official HEAD, `RtState::start_default_rules` registers `SimulateNpcs` before `NpcAi`. Rule binding appends handlers to the event-handler vector, and `emit` invokes that vector synchronously in insertion order. For an OnTick, `SimulateNpcs::on_tick` therefore examines and routes existing NPC-to-NPC `NpcAction::Msg` actions into the recipient `npc.inbox`; `NpcAi` runs afterward and may enqueue a new `RequestHire` message.

The server rtsim tick calls `state.tick`, then synchronizes Loaded NPC controllers to ECS agents in the same system pass. That synchronization takes all remaining `npc.controller.actions` and pushes them to the Agent rtsim-controller queue. `handle_rtsim_actions` has an empty `NpcAction::Msg { .. }` arm. Consequently, an NPC-AI Msg emitted after the SimulateNpcs handler can be drained into the Loaded Agent queue before the next SimulateNpcs pass, where it is ignored rather than appended to the recipient inbox. The A instrumentation and recruit patch preserve this handler order, Loaded handoff, and empty Agent Msg arm; the new recruit task still calls `ctx.controller.send_msg(target, RequestHire)`. This is a concrete static integration hazard consistent with the repeated `message_sent` followed by no observed Hire.

The raw telemetry does not instrument the exact queue dequeue or recipient-inbox insertion for each Msg. Therefore the lost-message path is strongly supported by synchronous code flow but not directly proven event-by-event from this run. The observed facts remain: six queued/sent events, five post-message expiries, one request still pending at cap, and no observed hired-member state.
