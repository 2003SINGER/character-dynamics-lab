# NCP-Bench：任务、源码协议与接入边界

日期：2026-10-07。状态：原论文正文/相关 prompt 定向审读、官方代码只读核验；**未运行 benchmark、未复现分数、未接入项目方法**。它进入核心评测候选栈，但不是已准入的 NPC 活人感评测。

## 结论先行

**论文证据：**该任务以电影规格提供初始事实、三类 narrative commitments 及有序 trajectory，测试 narrator 面对自由玩家输入时能否守住已建立事实及叙事约束。它可用来压力测试长程一致性；不直接评判可执行 NPC 的自主生活或玩家眼中的活人感。

**项目决定：**原 evaluator、终止和进度规则必须保留。将冲突改成“允许修复后继续”的任务可以另立，但不能拿修改后结果宣称赢了原 NCP-Bench。内部拒绝不合法提案后只提交最终回复是候选方法；外部 auditor 已发现冲突后再重试，是改评测协议。

## 2. 数据 schema：能复用的不是一个“剧情 prompt”

**源码证据：**[README 示例](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/README.md)及 `dataset/specs/movie52.yaml`。

| 对象 | 实际字段/含义 | 不要混成 |
|---|---|---|
| meta | 环境 ID/title/genre/player role | 角色局部观察 |
| initial_facts | content、稳定 id、negated | 完整游戏 ontology/preconditions/effects |
| commitments | description、type、satisfaction_condition、violation_condition；achievement/invariant/ordering | 本项目 RunningAction/task commitment；心理状态 |
| trajectory | id、description、trigger_event、key_delta | NPC 必须立刻执行的动作 |
| runner ledger | 活跃与已 negated 的 facts 均保留，方法只收 active facts | narrator 自行覆写的记忆列表 |

`achievement` 要求最终事件，`invariant` 约束特定阶段持续状态，`ordering` 限制事件先后。规格内容主要是自然语言，语义是否满足仍由 auditor/checker 判断，不是三类类型名自动带来确定性证明。

初始化所有 trajectory nodes 的 `occurred=False`。第一个节点是**待完成** milestone，不免费算成已达成；trigger 与 key delta 都成立才可推进。这也是固定源码版本的重要原因。

## 3. 单回合的真正读写顺序

主代理直接核验：[runner.py 固定源码](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/src/ncpbench/runner.py)，尤其 `start_episode`、`run_turn`、`apply_turn_outcome`、`run`。

```text
start_episode:
  narrator.start_episode → initialize state → narrator.open
  → opening evaluator 产出 pending fact updates
  → 开场文本进 history（turn -1）；updates 尚未提交

run_turn(player_input):
  从 committed state 构造 NarratorRequest
    [active_facts + commitments + trajectory/current_node + history + pending opening]
  将 pending opening 投影进 audit_context 的 ledger
  narrator.respond → 固定 evaluator.evaluate(response)
    conflict:
      返回原 session；不提交本轮事实/进度，不调用后两种 checker
    no conflict:
      投影 response fact updates
      → trajectory checker（看投影 facts + 加本轮后的 history）
      → 投影 trajectory assessments
      → commitment checker（看上述 facts/history + 新 trajectory）
      → commit [opening updates → response updates → trajectory/commitments/history]

run:
  每轮 player input → run_turn
  conflict → CONFLICT
  all achievement commitments satisfied → ALL_RESOLVED
  达 100-turn cap → MAX_TURNS
  最后 close narrator
```

这里 **runner 的状态转移是确定的，语义判断本身不是**。基准所有权是“固定外部协议控制 ledger”，不是“LLM auditor 对世界真值绝对正确”。格式非法的有限重试（最多两次额外尝试）不推进状态，不能与语义冲突后的修复混为一谈。

## 4. Baseline / HiAgent 到底改了什么

官方 `reference-methods/baseline` 与 `reference-methods/hiagent` 和 method-neutral runner 分离。以下是**本 benchmark 的实现**，不将 HiAgent 原论文细节直接倒灌。

| 源码入口（固定同一 SHA） | 实际读写/触发 |
|---|---|
| [BaselineNarrator](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/reference-methods/baseline/src/ncpbench_reference_baseline/narrator.py) / method prompt | 当前未发生 node 的 description/trigger/delta、commitments、active/pending facts、system-response-only history、当轮玩家输入；逐阶段推进，JSON text、150 词内；不是 request.history 原样全给 |
| [HiAgentNarrator](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/reference-methods/hiagent/src/ncpbench_reference_hiagent/narrator.py) | start 清空记忆并加入 Story initialized；open 走共享开场 prompt；respond 把上轮已返回文本记为 Action、本轮玩家输入记为 Observation，再组 turn context/run；只返回最终 Action 文本，存为下轮 pending action |
| [HiAgentCore](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/reference-methods/hiagent/src/ncpbench_reference_hiagent/core.py) | 模型输出新非空 Subgoal 才增加目标记忆并清检索索引；没有由 benchmark checker 触发的独立切换器。输出 retrieve(id) 则递归调用，被检索旧 subgoal 保留详细轨迹；max_retrieve_depth 限制深度 |
| [TrajectorySummarizer](https://github.com/NLP2CT/NCP-Bench/blob/780aeb559ce216a57cbd934b5a20bfd35018c4f6/reference-methods/hiagent/src/ncpbench_reference_hiagent/summarizer.py) / prompt serialization | 窗口含多个 subgoals 时旧轨迹变一行 LLM summary，当前或被检索的保留细节；过滤 check-valid actions。默认 summary 上限 220 字符但可配置；不是一次真实 completed event 更新 persistent ledger |

`make_prompt` 先取配置窗口，再按 max_input_tokens 裁最早 history chunks。子目标何时完成由模型按 observations 判断，检索也是模型请求，不保证检回遗漏的玩家意图。具体 parsing.py 的 ID 容错/边界未逐项核完，适配前仍需核验。

HiAgent context 复用 Baseline 模板但替换输出区块，另加 subgoal/retrieval 指令；固定 prompt 把玩家输入视为 in-world claim/attempt，不自动当真事实，并规定 narrative consistency 优先。因此是**记忆+控制 prompt 的具体对照实现**，不是只替换无副作用 memory module。源码审读与 benchmark 数字分层，未按原配置运行不称复现。

**论文 Table 3，PDF p.8：**两组各 100 episodes、同一 GPT-5.4-mini auditor，GPT-4o-mini 与在其上构建的 HiAgent 比较：

| 指标 | GPT-4o-mini | HiAgent | 读数边界 |
|---|---:|---:|---|
| 平均 interactions/turns | 22.16 | 30.05 | 每组 episodes 的均值，不是纯计算效率 |
| commitment conflict | 26% | 4% | 发生该类冲突的 episode 百分比，不是每承诺/每回合错误率 |
| player-input conflict | 13% | 38% | 同上，必须与 commitment 改善一起报告 |
| Succ. | 5 | 3 | 聚合“到上限”与“全部成就完成”，不是纯 completion |
| 全 achievement 完成 | 2 | 0 | HiAgent 的 3 次 Succ. 全是达到上限 |

这些数值不等于“记忆导致玩家输入冲突”的因果识别；作者的摘要丢局部意图解释是可能机制，不是已完成对应消融。主模型比较的 auditor 配置与此表不同，不能拼在一起算优势。

正式摘要的 GPT-5.2 “20 turns 后 survival 42%”、fact conflict 40%–68% 属原作者不同模型条件；**survival ≠ 完成全部承诺**。审计可靠性有 backbone 敏感性及 100 个最终结果的人类核验，不能据此推到所有中间回合、所有题材或玩家感受零误差。

## 5. 本项目十字段 benchmark 卡

| 字段 | 适用判断 |
|---|---|
| 控制问题 | 自由输入下 facts/commitments/trajectory 能否长期守住 |
| 保存对象 | benchmark-owned ledger、commitment status、有序节点、history；方法局部记忆另存 |
| 输入/输出 | 官方 StorySpec+player input → narrator text → external assessments/result |
| 触发 | 每轮回复固定审计；opening updates 只在首次合法提交时生效 |
| 搜索/修复 | 原 benchmark 不 repair；HiAgent 是记忆层，不是局部未来修复规划器 |
| 作者工作 | 结构化电影规格与语义条件；不是已可执行游戏域的免费替代 |
| LLM 可补 | narrator、对抗输入、审计；三者角色固定分开，不能被测方法自判 PASS |
| 可吸收 | 三类型约束、稳定事实 id/negation ledger、方法与协议分离、turn-wise failure accounting |
| 冲突边界 | W 中合法破坏 invariant 的玩家动作可能本就与固定剧本矛盾；未来允许换分支不能继续冒称原任务 |
| baseline/ablation | 原 baseline/HiAgent/项目候选共用官方 runner；repair 另设协议并单独计分，本轮未实施 |

## 6. 接入之前的最小验收，不在本轮开跑

**D：**接入有两条账，不混分数：

1. **Original protocol**：冻结上列 source/prompt/models/cap/player condition；方法只实现 narrator 边界；保留 CONFLICT/ALL_RESOLVED/MAX_TURNS，报告 survival、真实 achievement completion、节点进度、冲突类别以及 tokens/latency/cost。确定性小型 contract 可用假 narrator/evaluator 检查提交顺序，但不能当正式得分。
2. **Repair protocol（另议）**：明确哪些 commitments 可改、谁授权、玩家已发生后果不可撤销；评 repair 成功/变更量/角色目标连续性/预算耗尽/解释质量。原 benchmark 未提供这些效果的标注或玩家效度，不能拿它的映画 trajectory 当唯一合法未来。

W action executor 与 narrator text 不是一个接口。若把电影自然语言事实先编译成 W，domain 建模错误和缺失 action 必须单列；本轮没有给项目字段增加 Achievement/Invariant/Ordering，更没有创建 `S.distrust`。

## 7. 判定与未决

**D：**NCP-Bench 是很有价值的外部约束压力测试候选，优先级从外围标题筛查提升为 protocol/source 已核的比较候选；**未**升级为玩家活人感、动作执行有效性或低作者成本 benchmark。

**Q：**现有电影规格是否覆盖我们要的“允许玩家改未来而仍保留作者少数锚点”？应先纸面选一例区分 immutable facts、硬承诺与允许分支，不先跑 100 个电影。整个考古包的唯一下一动作由[总报告](专题调研_多粒度剧情连接与LLM重组_2026-10-07.md)维护。
