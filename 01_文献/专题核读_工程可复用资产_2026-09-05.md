## §0. 先说结论（四句话）

1. **代码是真的有，但只有 11 个包，而且只对得上 4 卷里的 2 卷**（V1 与 V3）。V2 与 OE21 一个 demo 都没有。
2. **其中对本项目的价值高度集中**：`N-gram` 库可以直接当**非理论基线**；`BackgroundAI` 小镇模拟器可以直接当**试验台底座**；`StochasticGrammar` 可以当**行为序列生成器**。其余 8 个包与本项目无关（寻路、编队、随机数、人群）。
3. **实验几乎不存在。** 全 146 章里，我做全文扫描后只找到 **1 个真人受试实验**（V3 C04）。其余所有命中"experiment / evaluate / we measured"的地方，指的是**架构里的"评估树"或"性能评测"**，不是科学实验。这一点必须说清楚，否则会高估这套书的证据强度。
4. **二阶知识（Theory of Mind）在全库零命中。** 不是"做得浅"，是**一次都没出现**。

## §2. 资产一：`ngram_lib` —— 直接可用的**非理论基线**

**来源**：V1 C48，Joseph Vasquez II，2012–2013。2 个文件，1762 行，header-only 模板。
**许可**：头文件里写着 `/// \par You can use it though`（非标准措辞，但作者明确表示可用。**若要正式使用建议先发邮件确认**——这是一句口语化授权，不是 OSI 许可证）。

### 2.1 接口（`ngram.hpp`）

```cpp
template <int N_value, int E_max_events>
class Ngram {
    void  Add_Event(int event);                      // 喂入一个事件（事件需编码到 [0, E)）
    void  Add_Events(int const* events, int length);

    int   Predict(void) const;                       // 预测下一个事件（argmax）
    int   Predict(float& probability_of_next);       // 预测 + 该预测的概率
    float Confidence(void) const;                    // 对自身预测的置信度

    float Probability_Next_Is(int event) const;      // ★ 给定事件的下一跳概率
    float Probability_Future(int const pattern[N]) const;  // 某完整模式未来出现的概率

    void  Use_Weighted_Random(bool enable);          // 按置信度加权随机采样（默认关）
    void  Use_Window_From_Event_Sequence(void);      // 用事件序列的隐式窗口（默认开）
    void  Use_Window(int const user_window[N-1]);    // 指定窗口 → 可用于条件生成
    void  Reset(void);
    int   Memory_Usage_Bytes(void) const;
};
```

### 2.2 为什么这个对本项目是**最实用的一件东西**

我们的主指标是 **ΔNLL**（留一预测：给定前缀，预测下一个行为）。要做这件事，必须先有一个**强基线**回答："不用任何心理学理论、不用 LLM，光靠序列统计能预测到什么程度？"

`Probability_Next_Is(event)` 恰好就是这个问题需要的函数：

| 我们需要的 | ngram_lib 给的 |
|---|---|
| 每个候选动作的条件概率 | `Probability_Next_Is(a_i)`，对全部 `E` 个动作各调一次即得完整分布 |
| 留一评测 | 逐事件 `Add_Event` + 预测，天然支持 online held-out 评测 |
| 与理论对照的**等参数**基线 | N-gram 的参数量可由 `N` 与 `E` 精确控制，方便做等参数对照 |
| 长程依赖的照妖镜 | N-gram 只能看 N 步；若我们的 `S` 在长程上显著优于 N-gram，**这就是"长程 O(1) 可用性"路径的直接证据** |

**这一点直接支撑 R01（预测充分性）**：
`p(A_{t+1}|H^obs_{≤t},O_t,P) ≈ p(A_{t+1}|S_t,O_t,P)` 要成立，必须证明 `S` 比"原始历史的统计量"强。N-gram 就是那个"原始历史的统计量"的最标准实现。

**具体动作**：把动作表编码成整数 id（`E` 个），跑 N=1..5 的 N-gram 留一 NLL，作为 R01 的**基线地板**。任何 `S` 方案必须显著低于这个地板才算有效。

**局限（必须同时记下）**：
- 事件空间必须离散且有限（`E` 是模板参数，编译期确定）。我们的行为若含自然语言，需先做**动作类型层**的离散化——这本身是个设计决策，不能假装没有。
- N-gram 没有`O`（观测）概念，无法表达"角色没看到"。**它天然做不到 `W ≠ O`**，所以它在"信息不对称"场景下的失败是可以预期的，不能拿它的失败当我们的胜利——要专门设计对照。

## §3. 资产二：`BackgroundAI` —— 可直接改造的**小镇试验台**

**来源**：V1 C36，David "Rez" Graham。45 个文件，10,758 行 C++，VS2010 + freeglut。

### 3.1 它是什么

一个**小镇模拟器**：绿色是住宅、蓝色是商业建筑、黑色三角是 NPC、黄色方块是"槽位"（slot）、右侧两片绿色是农场。顶部显示模拟时间。可加速（键 1–6）、点击 NPC 看信息。

**数据驱动**，三个 XML：

```
data/World.xml      — 世界布局
data/Objects.xml    — 对象定义
data/Schedules.xml  — 动作定义 + 日程模板
```

### 3.2 与本项目架构的逐项对照

| 我们的概念 | BackgroundAI 里的对应 | 差距 |
|---|---|---|
| `W`（权威世界） | `World.xml` + `GameObject` 树 | **有，且是数据驱动的** |
| `O`（局部可知视图） | **无** | NPC 直接读世界，**没有信息不对称** |
| `X`（结构化语义 / Appraisal） | **无** | 完全没有语义层 |
| `S`（角色状态，各字段自有动力学） | **无** | NPC 没有任何内部心理状态 |
| `D`（每轮决策上下文） | `ScheduleInstance` 当前条目 + 时间 | 只到"日程条目"粒度 |
| `π(A)`（行为分布） | 日程条目的 `Sequential` / `WeightedRandom` / `Simple` | **有，且是显式的三类** |
| 动作 | `ActionDefinition` / `ActionInstance` **分离** | 见下 |

### 3.3 三个值得抄的具体设计

**(a) `ActionDefinition` vs `ActionInstance` 的分离**

```cpp
class ActionInstance {
    const ActionDefinition* m_pDefinition;  // 静态定义（名字、目标类型、时长范围）
    float m_duration;                        // 本次实例的实际时长（从 min/max 间采样）
    int   m_index;                           // 在顺序模板中的下标
    bool  Update(float deltaTime);           // 返回 true 表示该动作结束
};
```

`Schedules.xml` 里：
```xml
<Action name="knead_dough" target="baker_counter" minDuration="0.5" maxDuration="1.5"/>
```

**这正是我们 Q06（承诺生命周期）需要的区分**：定义是可枚举的候选，实例是带自身状态的一次执行。**可以直接沿用这个切法**，我们的"动作质量 / 中断 / 部分失败"都挂在 `ActionInstance` 上，而"可用性 / 前置条件"挂在 `ActionDefinition` 上。

**(b) 日程条目的三类组合子**

```xml
<Entry name="BakerWorkTemplate"      type="Sequential">     <!-- 顺序：揉面 → 烤 -->
<Entry name="InnkeeperWorkTemplate"  type="WeightedRandom">  <!-- 带权随机：站柜台(3) / 擦桌(2) -->
<Entry name="SleepTemplate"          type="Simple">          <!-- 单一动作 -->
```

`WeightedRandom` 带显式权重——**这就是 `π(A)` 的最朴素形式**，可以直接作为我们 `π(A)` 的"零信息基线"：`S` 的作用就是让这些权重**随状态变化**。这一对照极其干净：**固定权重 vs 状态调制权重**，变量只有一个。

**(c) NPC 状态极简，且不含任何心理量**

```cpp
class Npc : public GameObject {
    Vec2 m_pos, m_velocity, m_lookAt, m_destination;
    ObjectOwnershipMap m_ownershipMap;      // 归属关系（我的床、我的工位）
    ActionInstance*    m_pCurrentAction;
    ScheduleInstance*  m_pCurrentSchedule;
    double             m_scheduleEntryEndTime;
};
```

位置、速度、朝向、目的地、归属、当前动作、当前日程、条目结束时间。**七样东西，全是物理/日程量，没有一个内部状态量。**

### 3.4 这一节最重要的发现：AI Town 的**底座**在这里，而且它没有内部状态

用户说：「斯坦福 AI 小镇的行为非常简单，但是爆火了。」

**现在可以精确说出"简单"是什么了**：Generative Agents（2023）的小镇，其**调度底座**（地点 + 日程 + 动作槽 + 移动）与 2013 年这个 `BackgroundAI` 是**同一套东西**。十年间被替换掉的不是底座，是**表面文本**——由 LLM 生成的观察描述、反思与对话。

换句话说：
> AI Town 的爆火，验证的是"**在既有调度底座上接 LLM 文本层**"的吸引力，**不是**"内部状态建模"的吸引力。

这与 V3 C04 的真人实验结论（`words sometimes speak louder than actions`，见 §5）**完全吻合**，而且是独立来源的互相印证。

**对我们的含义（双刃，必须两面都写）：**

- **正面**：我们要做的"给既有调度底座加真实的 `X → S → π`"的位置是空的，且人们确实想要更好的 NPC。
- **负面/警告**：如果我们的**评测**靠人类观感，那么我们加的 `S` 很可能**测不出差异**——因为爆火的那个版本根本就没有 `S`。**这直接支持"用留一预测而非人类评分"作为主指标的决策**，并且是迄今最强的一条支持证据。

## §4. 资产三：**评估与执行解耦**（可抄的思想，不是代码）

**来源**：V1 C10 §10.8 "A Twist on Behavior Trees: Evaluation versus Execution"

### 4.1 原文主张

> "The behavior tree coupled with this chapter differs from some traditional implementations in that it **separates the idea of tree evaluation from actual execution**."

由此得到两件事（原文第 10.8 节末尾）：

> "the ability to **evaluate the tree independently of an agent's behavior execution**. While an agent is actively executing behaviors, we can freely evaluate the tree in parallel without interfering with the executing nodes, and only interject if the results vary from the presently executing plan."

> "Evaluating the tree in its entirety also means we can optionally perform a limited version of **look-ahead planning**, since we can ensure that an entire plan is valid to the end, at least at the time of evaluation, before committing any of it to the agent."

附带的工程细节：utility selector **先验证子节点合法性再算效用**（"it must update utility only for valid children"），因此昂贵计算只花在合法候选上；叶子可在 `Evaluate()` 里算好并缓存，`CalculateUtility()` 直接取。

### 4.2 为什么这对我们不是可选项而是必需

我们的 `π(A)` 写的是**行为分布**，不是 `argmax`。要测分布，就必须在**角色正在执行 A 的同时**算出"此刻 B、C、D 的概率分别是多少"。

如果决策与执行耦合（传统 BT），执行中你只能看到被选中的那一条，**拿不到反事实分布**。

**结论**：评估/执行解耦是我们做**反事实评估（counterfactual evaluation）**的前提条件。这不是"可以借鉴的优化技巧"，是**评测协议能否落地的架构门槛**。

> **待办建议**：检查 `Demo codex-generated/` 的 `decision.h/.cpp` 与 `simulation.cpp`，确认当前实现是"选一个然后执行"还是"每轮对全部候选算分"。若是前者，R01 的留一评测现在就跑不起来——**这是比任何理论问题都更前置的阻塞项**。

### 4.3 【已核查 2026-09-05】我们的代码：**架构已解耦，但分布没落盘**

实际读了 `Demo codex-generated/`，结论比预想的好，但有一个精确缺口。

**好消息——解耦已经做到了。** `Src/simulation.cpp:146–160` 的每步流程：

```cpp
trace.decision      = decide(observation, state, personality);   // :156 每步都跑，无条件
trace.chosen_action = sample_action(trace.decision, action_rng); // :157 从分布里采样
```

两个关键点：
1. `decide()` **无条件每步调用**，没有被 `if (commitment.status == Active) skip` 之类的门槛挡住。所以**承诺执行期间 π(A) 依然在算**，反事实分布是拿得到的。
2. 采样与评估是分离的两个函数调用——`decide()` 产出完整 `DecisionContext`（含 `std::vector<CandidateAction> candidates`，每个带 `activation / threshold / probability / eligible / reason`），`sample_action()` 才做 `std::discrete_distribution` 抽样（`Src/decision.cpp:178`）。

**这正是 §4.1 要求的结构，我们不需要改架构。**

**坏消息——π(A) 在日志边界被扔掉了。** `Src/simulation.cpp:245` 的 CSV 表头是：

```
...pre_purchase_urge,chosen_action,accepted,elapsed_minutes,event_ids,outcome_task_id,...
```

只落了 `chosen_action`（采样结果），**每步候选的完整概率分布一个字段都没写**。

后果：**留一预测现在跑不了，但原因不是架构，是日志。** 分布每步都在内存里算出来了，然后在写 CSV 时被丢弃。

| 项目 | 状态 |
|---|---|
| 评估/执行解耦（架构） | **已满足** ✓ |
| π(A) 每步可得（含承诺期间） | **已满足** ✓ |
| π(A) 持久化到轨迹文件 | **缺失** ✗ |

**修复范围很小**：只动 CSV 写出部分，为每个 `ActionType` 加一列 `p_<action>`（或一个 JSON 列存整个分布）。不需要动 `decide()` / `sample_action()` / 状态更新逻辑。

> 这条从"阻塞项"降级为"**半小时的日志改动**"，但它**卡住了 R01 的全部实证工作**，所以在做任何其他评测之前先做它。

## §5. 实验资产：全库唯一的真人实验（V3 C04）

### 5.1 先说扫描结果：**全库几乎无实验**

对已提取文本的 47 章做正则扫描（关键词含 experiment / evaluat / measured / we tested / user study / playtest / we found that / benchmark）：

| 章 | 命中数 | 实际是什么 |
|---|---|---|
| V3 C31 Dragon Age 效用评分 | 73 | **全部是"evaluation tree"（评估树，打分架构）**，不是实验 |
| **V3 C04 玩家对 AI 对手的感知** | **18** | **唯一真人受试实验** |
| V1 C10 效用决策入行为树 | 13 | 公式推导与调参经验，无实验 |
| V3 C35 环境交互 | 10 | 系统描述与编译期反馈，无实验 |

**必须诚实记录：这套书是工程经验集，不是实验报告集。它的证据形式是"我做过，所以我知道"，不是"我测过，数据如下"。** 唯一的例外是 V3 C04。

### 5.2 V3 C04 的实验协议（可复用的部分）

**设计**：
> "Subjects were asked to play multiple games against each of **22 AI opponents**, tracking their wins. All games were played on the same day, and the order of opponents was **randomized**. After each set of games, they rated the AI opponent on **fun, realism, and difficulty on a five-point scale**. They also wrote a short explanation of what they felt the AI's strategy was."

**协议里可复用的四件事**：同一天完成（避免跨时段漂移）、**对手顺序随机化**、**五点量表**的主观打分 + **开放式短答**、以及**用开放式回答做识别度评分**（而不是只收量表分）。

**识别度的评分方式**（这点尤其值得抄）：
> "Full points were given if they described something roughly similar to one of the main points of the AI's strategies and partial credit if they described a relevant, if not core, aspect of the strategy. We were rather lenient on grading but even so... **strategy recognition was nearly nonexistent.**"

### 5.3 实验结果（三条，逐条看对我们的含义）

**(1) 83% 的玩家认不出一个纯随机数生成器**

> "**83% of players were unable to recognize an AI that was literally nothing more than a random number generator.**"

> "It is our opinion that this is an important finding—**players have no idea what your AI is doing**."

**含义**：**人类感知是一个低分辨率信道**。若我们最终以"人类觉得像不像"为主指标，测不出 `S` 的贡献是**大概率事件**，不是意外。这是对"留一预测作主指标"的**正面支持**。

**(2) 享受度与实际/感知难度、智力、真实感都不相关**

原文结论：享受度与 AI 的真实难度、感知难度、感知智力、真实感、策略识别度**均不相关**；一个纯随机 AI 在"最好玩"上**并列第二**。

**含义**：我们不能用"人类更喜欢"来论证 `S` 有价值。**这条路在这套数据里已经被走过并失效了。**（注意：这是 2017 年、非叙事类、对战场景的数据，见 §5.4 边界。）

**(3) 玩家会主动编故事**

> "**Players invent stories for the nonplayer-controlled characters in the game. They see cheating, bias, motivations, and desires where none exist.**"

> "Many players might not recognize or appreciate an AI that flanks them (the AI behaving intelligently), but they do appreciate when an AI explicitly shouts 'let's flank them' (the AI claiming it is behaving intelligently). **In game AI, words sometimes speak louder than actions.**"

**含义**：这条**同时**解释了两件事——
- 为什么 AI Town 能爆火（表面文本的叙事可读性 >> 内部保真度）；
- 为什么我们**绝不能**用人类评分当主指标（人类评分测的是叙事可读性，不是机制保真度）。

### 5.4 边界（不做这些限定就是过度外推）

- 场景是**对战型 AI 对手**，不是叙事型 NPC。**玩家与 AI 是对抗关系**，与"观察一个 NPC 的生活"动机不同。
- 时间是 2017 年，早于 LLM 角色模拟。
- 受试规模、招募方式在章节里**未完整报告**（我未看到 n 数的明确表述）。**引用时必须标注为"[原始文献未完整报告]"**，不能当成大样本结论。
- "words speak louder than actions"在文本域的成立性**未被该实验检验**（该实验无文本对话 AI 条件）。它与 AI Town 的吻合是**旁证**，不是验证。

### 6.2 这个空白是**哪一类**空白（必须分清，否则会误判创新性）

| | 说明 |
|---|---|
| **是** | 游戏 AI 工业界**主动不做**二阶知识。原因是 Gap 1a：玩家看不见，做了不划算。这是**有理由的放弃**，不是疏忽。 |
| **不是** | 学术界没人做。Theory of Mind 在发展心理学（Wimmer & Perner 1983 Sally–Anne）、心智理论 benchmarks、以及 LLM 时代（SocialIQA、ToMi、Kosinski 2023 等）有**大量**工作。 |

**所以正确的定位是**：二阶知识不是"我们发现的无人区"，而是"**游戏工业界有理由放弃、学术 ToM 有大量成果、但两者没有接上**"的接缝处。我们要做的是**把学术 ToM 的表征接进游戏式的可执行架构**——这个接缝确实是空的。

**这修正了我在上一页可能给人留下的印象。上一页说"工业界没做"是对的，但若据此宣称二阶知识是创新点，条件是必须先做完学术 ToM 的调研。在调研完成前，本条只能登记为"候选"，不能登记为"创新"。**

> **待办建议（新）**：二阶知识需要一次**独立的学术 ToM 调研**，不能靠 Game AI Pro 支撑。重点不是"要不要有"（用户已确认要有），而是**深度取多少**：
> - 一阶：`A 知道 f`（我们已有 `O`）
> - 二阶：`A 知道 B 知道 f`
> - 三阶：`A 知道 B 知道 A 知道 f`
>
> 心理学证据是**人类在自然对话中可靠使用二阶、三阶显著吃力且极少**。若我们上三阶，可能是在建模一个人类都不用的能力——这需要在机制说明里写明理由，否则是被审查者质疑的点。
