## 1. 这轮究竟推进了什么

**E：**“节点之间自动连接、人物有自己目标、玩家破坏未来时重接、导演优化干预、作者预写内容与自由生成混用”各自都有成熟先例。WhatELSE 尤其已有**抽象 outline→固定可执行动作实例→模拟世界执行反馈→重新生成**，节点间也有自由 NPC 动作。因此“LLM 提案 + World 验证”本身不构成已确认差异。

**I：**LLM 可能降低旧系统里 refiner/缺失动机事件的提案成本，这是值得探查的切口；它没有自动消除 domain 建模、动作验证、人物模型拟合、作者审阅和调试。不能从“能给三个好主意”推出“总劳动少了”或“人物连续性已经解决”。

**D：**不抢着发明 planning algorithm，也不把项目缩回纯对话写作。用旧算法的可解释结构拆一个作者节点被玩家影响的情境，再判断手工瓶颈是否真存在。世界中心 NPC 仍是体验目标，低作者成本是待测贡献方向，不是替代目标。

## 2. 用户新增想法，与模型方案分开

**用户确认的探索要求：**作者不必只打孤立点，可以混用节点、趋势/线、亲写连续片段；中间由角色/世界或 LLM 候选补足；多角色各有经历，玩家作用可能替换之后的某段未来。这些由[机制 owner Q10](../00_研究设计/未决问题与机制候选.md#q10-稀疏作者约束与世界干预)维护。

**尚未选择：**节点究竟是世界状态、事件模式、段落还是 guard→作者 change；曲线用何时间轴/容差；作者 locked passage 是否可中止；分支替换何时获准；人物目标/知识/承诺连续性如何比较；选择 MPC/MCTS/POCL/utility 哪个。讨论中的表达式和 schema 只是候选，不直接进 C++ 或科研主张。

| 粒度 | 一个可讨论的具体语义 | 必须回答的冲突问题 |
|---|---|---|
| 点 | NPC 当面获知某消息/完成一次交易 | 状态成立但角色不知是否算到达？事件重复如何计？ |
| 线 | 从敌对到可交谈，或谜底逐渐披露 | 用 wall-clock、事件数还是 arc index？软趋势不能压过硬事实 |
| 连续 locked 片段 | 作者亲写的见面、争论、离场 | 玩家杀死参与者或毁掉道具后，还强播吗？允许中止/换分支吗？ |
| 分支 | 原 future 因道具被毁换成另一条支持链 | 只改未执行部分？保留哪些角色 goals？无解怎样展示？ |

这张表是**需求拆解，不是新 schema**。把全部对象塞进“统一约束语言”会先增加编译/诊断成本；应以现有表达能否覆盖实例判断，而不是以概念多算创新。

## 4. Storylets 与社会模拟：预写块怎样进入持续世界

**E（继承前轮）：**CiF 保存交换模板、条件加权规则、参与者绑定及历史 SFDB；microtheories 复用理由，交换满足前提后按发起者/响应者分数选择效果与文本 instantiation。Versu/Praxish 把 activity roles 与可选动作暴露给人物，再由人物 utility 选；Praxish 已核原件是一步绝对后状态评分，不能借它填 Versu 未公开的完整选择法。原始 sources/条件/公式在上述算法卡。

**I：可借结构**是 `entry conditions → authored content/actor options → committed effects → history`。保存的是可用块、角色绑定、使用进度与真实后果，不只是随机播作者片段。触发由 entry 判定；选择/优先级/重复控制仍由具体系统定义；玩家改 W 后必须重新检查入口与正在播片段的继续条件。

**作者负担：**块内容、条件、effects、互斥与调试仍存在；粗粒度块好写却难处理中途破坏，细粒度库可组合却增加规则测试。现有 CiF/Versu 证据不普遍证明从任意作者文本自动得到完整 actions/domain。可比较“同一内容库的选择法”和“同一选择法的内容组织”，不能同时改两者后归因复用。

## 5. 现代系统逐算法比较

### 5.1 三种“桥接”不是一个东西

来源：WhatELSE [CHI 2025 作者 PDF](https://www.research.autodesk.com/app/uploads/2025/02/WhatELSE.pdf)；Drama Llama [arXiv v1](https://arxiv.org/pdf/2501.09099v1)；Narrative Studio [WNU 2025 正式论文](https://aclanthology.org/2025.wnu-1.16/)。WhatELSE 方法/用户研究定向审读，不是 18 页全部附录逐项精读；Drama Llama 正文及 trigger 示例定向审读；Narrative Studio 父代理全文文本审读含 prompts，未运行源码。

| 十字段 | WhatELSE | Drama Llama | Narrative Studio |
|---|---|---|---|
| 控制问题 | 作者选叙事空间与抽象度，转成能玩的环境 | 自然语言 storylets 支持开放文本响应 | 在事件树中探索较好的故事发展 |
| 数据结构 | pivot/outline/variants、分层抽象、game W/角色 memory/固定 schema | setting/cast/transcript、condition/unused action text/type | event tree、ancestor path、entity relationship graph |
| 输入→输出 | outline/current W/memory → 动作序列→新 W | transcript/conditions → next stage-direction text | fragment/instructions/entity graph → candidate events |
| 触发 | 下一 outline 事件及玩家改动后的新生成；节点间自由行为 | 每条消息后顺序检查 active triggers，首个匹配触发 | 搜索扩展/选择，非 runtime event clock |
| 搜索/修复 | LLM compiler→game execution feedback + coherence/motivation reviewers→修订 | LLM 判断条件；用一次 action 文本后 inactive，ending 停；不是形式 repair | UCB1/MCTS、LLM expand/rollout、LLM 1–10 reward，backprop；临时 rollout 节点丢弃 |
| 作者工作 | 域/角色/outline/操作与调整抽象范围 | 人写 trigger、文本序列、设置并试跑/迭代 | 约束/guide/实体关系及评审标准；后向因果拓展未充分评价 |
| LLM 位置 | 动作实例/序列提案和软 reviewer | 条件识别、人物文本生成 | 事件提案、rollout 和 judge |
| 可吸收 | 抽象范围控制、proposal→simulation→feedback | condition 与 locked text 分离、用过状态、ending 类型 | 显式候选树/探索预算/来源轨迹 |
| W/O/history 冲突 | reviewer 可看 current W+memory，未说明严格 actor mask | 主要 transcript，无硬 W action validator | entity graph 进 prompt，不是硬 effects executor |
| 比较证据/用途 | 12 人 authoring/play 两条件；可作最直接近邻，非总成本已证 | 6 位作者初步体验，timing inconsistency；文本 storylet 对照 | 20 个故事片段、10 events、LLM judge；搜索基线非玩家效度 |

**E：WhatELSE 的重要纠偏。**固定六动作接口为 move/speak/kill/attack/think/save；模型给实例/序列，未定义新的可执行 operator。Game Environment 实执行并回报失败，是真外部反馈，不是纯 co-writing；正文却没有完整公开逐动作形式化 pre/effect validator，不能夸成已复现的硬证明。节点间 NPC 可自由生成行动。参与者是 **12 人，不是 12 位论文作者**；作者 3 人。更愿意减少后续编辑是自报，固定 15-min outline 任务不是总工时测量。WhatELSE 与 Elsewise 2026 是不同工作。

**E：Drama Llama**的 actions 是预写 stage-direction 文本，不是游戏函数。多个满足条件时原顺序优先；未用完 action 时每次只取下一条，用尽则 inactive。与传统 storylet“条件+内容+effects”相似的作者接口，不代表它已给可执行世界层。

**E：Narrative Studio**的 entity graph 用来 grounding prompt；附录 constraints 通过 judge 惩罚，不是 W 的硬拒绝。LLM 给评估分数并不产生外部行为真值。20 fragments/10 events 的自动评价与更大搜索预算不能宣称证明 author cost 或玩家生命感。

### 5.2 LLM-Modulo 把验证负担放哪里

**E：**Kambhampati et al.，[*Position: LLMs Can't Plan, But Can Help Planning in LLM-Modulo Frameworks*](https://arxiv.org/pdf/2402.01817v3)，ICML 2024 position paper，主代理定向审读 §§3–4；不是本文提出的 NPC 方法。

保存候选 plans、domain models/specifications 和多种 critics；输入问题→LLM guess→hard/soft critics→backprompt controller 汇总反馈→再猜，hard critics 全许可才返回。hard 例是 VAL/资源/时间/模拟校验，soft 包括风格/可解释偏好，可由 LLM 辅助。完整性取决候选覆盖，正确性只继承相应 hard critics 及**被核模型**；paper 不承诺任意语言心理描述可证明。

作者/domain expert 仍须审定 preconditions/effects 和不完整问题规格。LLM 可参与模型提取、refiner 候选、格式转换及反馈组织；不能在同一失败后把 domain 放宽，再称通过旧约束。已有传统求解器可处理的任务，论文自己提醒其可能比 LLM 更省资源。因此“把 LLM 替进 refiner”是接法候选，须测收益/费用，不预定赢过传统 solver。

## 6. 一个多粒度情境，逐门决定谁该改

**I：自制纸面例，不是训练数据或实验结果。**作者希望商人最终交出欠款账本（Achievement），在会面前不能公开债主身份（阶段 Invariant），先拿到借据再揭露身份（Ordering）。亲写会面段落可中止，不允许复活死人/撤销玩家成功；商人原有“保住家人/经营店铺”目标，玩家成功烧毁唯一借据。

| 判定门 | 结果如何产生 | 失败不能被怎样掩盖 |
|---|---|---|
| 因果门 | 标出 `借据存在→会面核债` 支持边被烧毁打断 | 不把“作者希望核债”当借据仍存在 |
| 未来门 | 候选换成另一个已存在证人的证词/交易记录，或作者允许失败分支 | 不补造此前复印件；真正新增域要记人工批准 |
| 人物门 | 商人是否知证人存在、是否愿泄露、是否需先解除威胁 | 不因为 planner 需要配合就改 goal/reward/信任量 |
| locked 片段门 | 前提已坏则暂停/改为作者批准替代片段 | 文本“写死”不允许硬播违反 W 的动作 |
| 选择门 | 对合法且作者允许的候选比较 goal-set change/干预数/操作预算/叙事偏好 | Jaccard 小也不覆盖执行或玩家控制门 |
| external eval 门 | 若走原 NCP，使用原判定终止；若容许换 Ordering，另设 repair 任务 | 不能重写电影约束，再报 original completion 改善 |

这一个例子已经能暴露“修因果、补动机、增内容、改作者规格”四种不同劳动。LLM 多提候选只能直接减少其中的想法/文字草拟成本；最终总劳动/运行成本尚无证据。

## 7. 可吸收/候选研究/现在不做

**可吸收而不冒称创新：**causal-link threat、future-only repair、固定历史保护、DM action+null+操控成本、intent frames、belief-effect gap、goal-set distance、可执行 action schema 及 generate/test/critique、benchmark-owned ledger。

**候选研究切口（Q）：**在同一冻结域和作者不可改集合下，LLM-assisted refiner 是否减少未预写情境的新增事件/映射劳动，而不提高审核/调试/运行成本，不破坏玩家已生效后果和角色目标？目前没有选定最终方法，更没有证明这组合具有新颖性。

**本轮不做：**不改变 Runtime/Reference/Demo 参数，不修改人物 schema，不训练 policy，不运行电影 benchmark 或 64-actor 批次，不招玩家，不把 AI consensus 当效度。

### 候选比较怎样避免“更多模块当然更好”的自证

上一轮讨论的 A=纯 LLM、B=LLM+structured commitments、C=可执行 W+人物+在线 repair 可以作为系统级条件，**不能只凭 C 好就归因某一个机制**。C 同时改变状态、候选、执行和修复；应先有传统固定域 planner/refiner 的强对照，再在相同域、候选/预算/权限/展示下逐项隔离。若模型只是复述已经预写的好桥，记为内容库贡献，不记成在线创造。

| 评价维度 | 可观察/记账对象 | 不能替代它的东西 |
|---|---|---|
| Author intent | 预先规定的点/顺序/禁区及允许失败，分项达成 | 事后把目标删掉，或 generic completion |
| World causal validity | 执行 pre/effects、不可改事实、时序和资源 | LLM 说“合理”；文本补出未执行动作 |
| Character continuity | goal/knowledge/未完活动支持与具体突变反例，最终需体验评价 | Jaccard 或自创 trust 分数一票验收 |
| Player agency | 已接受玩家行为的后果实际保留，反事实未来随之改变 | 更流畅对白；把成功改失败来保剧本 |
| Dramatic quality | 目标玩家对相同展示的评价，合法但无聊的负例 | 原作者 evaluation function 被 optimizer 拉高 |
| Authoring effort | 新内容/算子/映射、审核/调试修改与实际时间；运行 tokens/延迟另账 | trigger 数或主观“愿意少改”自动当工时 |

这是冻结实验前的评价要求整理，不是已经选好样本量/评价器或获批运行协议。NCP 只能覆盖其中部分约束一致性，不能用它的 survival 代表全部六维。
