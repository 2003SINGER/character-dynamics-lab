**LIGHT 入口的真实差异。**固定源码 [`play_map.py`](https://github.com/facebookresearch/LIGHT/blob/71a06cae8573048b1af41507ac52fe33b650fab3/scripts/examples/play_map.py) 用 Hydra：

```sh
# 候选原生探针命令：尚未本机运行，不是成功记录。
python scripts/examples/play_map.py
python scripts/examples/play_map.py builder.load_map=scripts/examples/complex_world.json
```

README 的旧 `--load-map` 示例不能直接当固定源码的 CLI 契约。默认 `OnEventSoul`；没有 DIALOG model 时只允许 OnEvent/Repeat soul。这能支持“先不加载模型”的探针，但代码仍 import 模型相关模块；[requirements](https://github.com/facebookresearch/LIGHT/blob/71a06cae8573048b1af41507ac52fe33b650fab3/requirements.txt) 仍含 torch、ParlAI、Mephisto 等依赖，不能将“无模型推理”写成“无 ML 依赖/轻量安装”。

[`World.parse_exec_internal`](https://github.com/facebookresearch/LIGHT/blob/71a06cae8573048b1af41507ac52fe33b650fab3/light/world/world.py#L863) 的实际路径是解析命令→查 EventClass→`attempt_parse_event` 的参数绑定/事件构造→ErrorEvent 时只向 actor 反馈，非错误才 `parsed_event.execute(self)`。这提供真实执行入口，**不自动提供我们所要求的不可变 receipt、完整覆盖 seal 或私有信念**。解析异常分支还有 `/home/ubuntu/light_errors.txt` 路径，Mac 异常处理需探针确认；不可据此先大改原件。

## 2. 人物机制：到计算和写入层

### FAtiMA Toolkit：事件评价与人物动作选择候选

固定源码 `56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f`，Apache-2.0、C#。这是 [GAIPS Toolkit](https://github.com/GAIPS/FAtiMA-Toolkit/tree/56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f)，不能把 2012 Java FAtiMA 论文的全部规划/学习能力自动记给当前 Toolkit。

现有[方法审计 §2.5](算法拆解_NPC方法与生产系统_2026-10-07.md)已核对：[`EmotionalDecisionMakingAsset.Decide`](https://github.com/GAIPS/FAtiMA-Toolkit/blob/56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f/Assets/EmotionalDecisionMaking/EmotionalDecisionMakingAsset.cs) 枚举条件层/绑定；[`ActionRule.GenerateAction`](https://github.com/GAIPS/FAtiMA-Toolkit/blob/56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f/Components/ActionLibrary/ActionDefinition.cs) 将动作、目标、priority 具体化，源码 utility 是 parsed priority 加 minimum certainty；[`RolePlayCharacterAsset.Decide`](https://github.com/GAIPS/FAtiMA-Toolkit/blob/56b7cbd992f953cfe21a7b12cb1a0e6cdf6ccf9f/Assets/RolePlayCharacter/RolePlayerCharacterAsset.cs) 保留 committed action，否则最大 utility 并列候选打乱后优先。不是一句“有情绪所以会自主行动”，也不能写成全部候选降序排序。论文与代码评分差异仍分版保留。

官方组件包括 appraisal/beliefs/emotions、情绪决策、social importance、RolePlayCharacter；原 `Tutorials/` 与 `Tests/` 是复现入口候选。**本轮没有核实单个 headless 教程的完整启动命令或运行结果**。接 LIGHT 前需原例确认：外部事件如何投影进个人知识/评价、何时更新 emotion、Decide 输出怎样提交动作、失败反馈怎样更新。不能用现有手写 S law 填空后称 FAtiMA 复现；也不能假定 Toolkit 已替我们做多步 GOAP。

### Ensemble：共享社会记录、动机累加与动作语法

固定源码 [`8b74bdec4ba2ef4e14795b7591df3b5d73f283e3`](https://github.com/ensemble-engine/ensemble/tree/8b74bdec4ba2ef4e14795b7591df3b5d73f283e3)，官方 `ensemble-engine/ensemble`，JS、BSD-4-Clause；不是同名 Web3 或 agent 编排仓库。

| 运算 | 固定源实现 | 适配时不能偷换什么 |
|---|---|---|
| 社会记录与历史 | [`socialRecord.js`](https://github.com/ensemble-engine/ensemble/blob/8b74bdec4ba2ef4e14795b7591df3b5d73f283e3/ensemble/socialRecord.js)：按 category/type/first/second 写 predicate；支持数值范围、双向关系；推进 step 时复制持久事实、递减/结束有限 duration | 是共享 social record；first/second 不是“谁知道该事实”。不能直接宣称已有 actor-private O |
| 规则绑定/评价 | [`RuleLibrary.js`](https://github.com/ensemble-engine/ensemble/blob/8b74bdec4ba2ef4e14795b7591df3b5d73f283e3/ensemble/RuleLibrary.js)：枚举 cast 的角色绑定，检验条件；trigger 匹配后写 effects | trigger 会改社会状态，不是仅返回解释；应用方要排程调用 |
| 动机 | 同文件 `calculateVolition`：为 cast 建 volition set；匹配 volition rules 后 `adjustWeight` 累加，保存规则/条件来源，注册排序结果 | 是规则权重累加，不是训练 policy、连续心理动力学或一般价值学习 |
| 候选动作 | [`ActionLibrary.js`](https://github.com/ensemble-engine/ensemble/blob/8b74bdec4ba2ef4e14795b7591df3b5d73f283e3/ensemble/ActionLibrary.js)：按 volition 搜索动作语法与角色绑定，选 terminal，最高分并列绑定有随机选择 | terminal social action 不等于一整段移动/取物/送信计划；重放需记录随机选择 |
| 真实效果 | `doAction(boundAction)` 遍历 effects 调 `ensemble.set` | 这是社会库写入，不是 LIGHT 已接受物理动作。迁移时必须确定谁有权写哪类事实，不能两边各结算一次 |

原库需要应用显式调用 `calculateVolition→getActions→选择/doAction→runTriggerRules→setupNextTimeStep`；后两步**不是** `doAction` 自动执行。顺序是候选应用排程，不是库保证全链自动运行。原 [`ActionLibraryUnitTests.js`](https://github.com/ensemble-engine/ensemble/blob/8b74bdec4ba2ef4e14795b7591df3b5d73f283e3/tests/js/ActionLibraryUnitTests.js#L102) 说明旧 `testDoAction` 与新接口不兼容而不启用；其他 action 测试含手工 set effects。因此不能拿“仓库有 tests”保证 public doAction 已有完整原件验收。本轮未执行这些 tests。

## 4. 怎么推进才产生知识，而不是继续“准备研究”

1. **原生复现准入。**固定版本，在隔离环境跑 LIGHT 原地图以及选定人物框架的一个原例；保留安装/启动失败。看到初始观察、合法动作、实际变化和人物原参考行为，才进入适配。LIGHT 不能低成本运行就明确记录后换候选，不围绕归档库大修。
2. **有限传统组合基线。**在真实游戏里连接上表必要各层；限定地点/角色/合法干预，不开发完整插件平台。送信/守卫只是模型提出的情境，需先确认原行动和证据足以表达，不先编一条必须成功的剧情。不能在只跑通玩家地图时称这一阶段完成。
3. **诊断与比较。**先分清平台/接线错误，再对平静、打断、隐藏变化、合作/拒绝等匹配条件记录轨迹、未来修订、有效进度、作者干预次数/成本和失败原因；后续 Director-off、人物机制替换、历史消融保持相同权限与预算。基线能做到就承认，不能把省略原机制造成的失败当创新动机。

任务内 replanning 不等于跨任务提高方法；系统可运行不等于人物可信。全链覆盖后才有对象定位科研问题，玩家体验/作者总劳动仍需独立证据。当前不训练，不跑正式实验，不修改 frozen Runtime，不把已有蓝图当必需 implementation checklist。

**本轮停止点：**核查并修正路线，交付此表，未启动原生复现。唯一下一动作由 [TODO](../00_研究设计/TODO.md)维护：确认范围后做上述原生复现准入，而不是再写一篇宏观综述或默认部署 MC。
