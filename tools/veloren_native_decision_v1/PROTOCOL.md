# Veloren Native Pirate Recruitment — limited integration protocol

Status: Python adapter/runner draft for parent review; no native server launched.

## Aim and boundary

Compare the same existing Veloren save under native-only recruitment decisions (OFF) and a local Python GTPyhop HTN proposal adapter (ON). This is a bounded causal integration check, not a statistical comparison: Veloren draws native NPC RNG every tick, so matching save/seed does not imply matched trajectories. No new game rules, candidates, jobs, relationships, or completion facts are introduced.

The fixed source is Veloren v0.18.0 build commit `1d12f35edd6cdbfc1fb921c167cdd7beeeffe248`, with the source patch/build hash to be supplied in an immutable freeze file after the parent finishes the single Rust build. The Python adapter uses the existing local `gtpyhop-core==2.0.2` environment at `_local_data/native_platform_v0/evennia/venv`; it adapts P3's GTPyhop HTN pattern but does not import or imitate an Evennia instance.

## Native interface v1

Recruitment input is one JSON object per line:

```json
{"version":1,"kind":"RecruitMember","request_id":"<unique>","source":"character-dynamics-htn-v1","leader_uid":476,"target_uid":475,"observed_time":123.0,"ttl_seconds":60.0}
```

The server revalidates native legality. The request deliberately contains no caller-supplied faction, job, relationship, distance, or completion claim. `observed_time` is RTSim simulation seconds; it must be finite, non-negative, not future-dated, and no more than 10 seconds old. TTL is positive and at most 120 seconds. The Python controller uses 60 seconds.

Recruit view/request handling is enabled only when all three variables are set: `VELOREN_NATIVE_RECRUIT_REQUESTS`, `VELOREN_NATIVE_RECRUIT_EVENTS`, and `VELOREN_NATIVE_RECRUIT_LEADER_UID=476`. Without the complete set it is fully off. The configured leader allowlist is exactly UID 476. The server emits one `native_recruit_actor_view` per second for that leader. The v1 view fields are `version`, `time`, `npc_uid`, `mode`, `role`, `job`, `home_site_id`, `current_site_id`, `leader_at_home`, `eligible_recruits`, `hired_members`, `hired_member_count`, `native_recruit_population_guard`, and `native_recruit_raid_site_available`. Site/faction IDs remain opaque diagnostic strings or null; Python requires the explicit native `leader_at_home=true` gate and matching non-empty home/current diagnostic strings before proposing.

- The view is actor-local and restricted to the selected Pirate leader and legal candidate set: alive, uncommitted Pirate(false), same home/faction, and within 24 m according to native validation. Candidate rows contain `npc_uid`, optional `distance_3d`, and `mode`.
- `hired_members` contains only alive same-leader `Job::Hired` members actually visible within 24 m; rows contain `npc_uid`, `distance_3d`, and `mode`. `hired_member_count` must equal this local array length. This is a current local observation, not a persistent roster. The controller stores UID→last-observed-time history only as history and never treats it as proof the NPC remains hired or nearby.
- `native_recruit_population_guard` is only the native existing guard result; no remote population identities or counts are exposed to the planner.
- `native_recruit_raid_site_available` is a read-only boolean for the existing native nearby-raid-site gate. No random site is selected and no RNG is consumed by reporting it.
- OFF and ON use the same view/request/event paths and the same read-only observer/persister setup. OFF logs views but never invokes the planner or appends a recruitment request. ON may append requests; there is no CancelRecruit input. TTL/native interruption and the native action's `on_cancel` path govern termination.

Native progress events include `native_recruit_request_accepted` (admission only), one-time `native_recruit_started` (native AI action began), `native_recruit_message_sent` (message sent, not completion), `native_recruit_job_observed` (actual target `Job::Hired(Actor::Npc(leader))` observation attributable to a request), and `native_recruit_terminal`. A separate `native_recruit_unattributed_hire_observed` records a natural hire that occurred without this request's message; it remains a real native observation but not a causal success of the external task. A `native_recruit_request_rejected` is matched by unique request ID (and verifies leader/target if echoed); job and terminal events require matching request ID plus leader and target. The terminal outcome `hired_observed` is valid only after the request started, its message was sent, and the target's native Job was observed. Expiry outcomes distinguish `expired_before_native_action`, `expired_after_native_action_before_message`, and `expired_after_message`, with `leader_invalidated` and `target_invalidated` for native interruptions. No accepted or message-sent event alone counts as a hire.

## Planner contract

Input is exactly one current `native_recruit_actor_view`. The high-level symbolic goal is `nativeparty`: four currently locally observed `Job::Hired(leader)` members, reflecting the existing native raid-preparation threshold. The goal is not satisfied from messages, accepted requests, historical observations, or remote roster state.

The symbolic overall goal `nativeparty` remains four currently locally observed `Job::Hired(leader)` members. The executable HTN is deliberately receding-horizon: it solves only `make_one_native_recruitment_progress`, not the four-member goal. Its alternatives are `already_enough` (for the one-step subtask) and `recruit_one`; candidate-specific methods use deterministic order (known 3D distance, then UID), and GTPyhop iterative DFS/backtracking lets a prediction primitive fail its precondition for an excluded/already-hired candidate and try the next candidate. The primitive's predicted effect is explicitly hypothetical: one hire-count increment and removal of that target from predicted eligible candidates. At least two eligible, untried candidates must be visible before selecting. The output status `SOLVED_NEXT_SUBTASK` means only that one prediction-only high-level `RecruitMember` task was proposed; `overall_goal_satisfied` remains false. Veloren retains approach, message, Brain/Agent execution, and all state settlement. A fresh view plus native job/terminal feedback drives the next proposal. The adapter never writes `Job::Hired` or marks an action complete. The native receiver/acceptance policy is unmodeled.

After a fresh view shows at least four currently visible hires, the controller sends no further requests and returns control to the native NPC. It does not send `EndHire`. The run then observes up to 20 seconds of native continuation. If members cease to be locally observable, no claim is made that they remain present. If the goal is not reached within the fixed trial budget, preserve the partial outcome; do not change seed, reload, or retry the world.

## Pair design and limits

1. Parent prepares two independent userdata copies from the same read-only source save. Both must have identical map/settings/source-world hashes and seed; their userdata roots and output directories must be distinct.
2. OFF runs first for at most 360 wall seconds with the same native observer/persister and recruitment ActorView configuration as ON, and an empty recruitment request file. Its Python side records ActorViews only and never invokes GTPyhop.
3. ON runs once for at most 360 wall seconds, using the same observation/persister configuration, with a new empty request file. Before the first proposal, it requires a fresh ActorView for the leader and at least two eligible Loaded candidates, plus three distinct native baseline snapshots spanning at least two wall seconds where the leader and those candidates are alive, Loaded, and have finite ECS positions. This readiness check does not require SPEAK capability or `allowed_to_speak`; recruitment uses the native RTSim hire message, not the Talk action. If the prefix is not achieved before the fixed trial cap, preserve the run as not-ready; do not start a second server or treat simulated-only candidates as proof of Loaded entity execution. Once ready, the planner uses only eligible candidates whose ActorView mode is Loaded. It uses at most eight unique candidate requests, one in-flight request at a time, TTL 60 seconds, and never retries a previously submitted target in that run.
4. Maximum server launches: two total (one OFF, one ON), sequentially. No restart after a valid launch, no seed/RNG manipulation, no world teleport, no GUI/client, no public server/account, no build from this runner.
5. Before either launch and throughout each run, stop if free disk falls below 6 GiB. Stop at 360 wall seconds. Recruitment telemetry cap: 10,000 rows / 16 MiB; process logs are also monitored under the same 16 MiB aggregate budget. A run uses a unique, non-overwriting directory.
6. Stop ON early if four hires are currently visible, then observe native continuation for 20 wall seconds; or if the view reports fewer than two untried candidates, the request budget is exhausted, or a safety limit is hit. Preserve all prior outputs.
7. Each server receives SIGUSR1 only by its exact child PID, configured with a one-second grace. Record signal time, natural/fallback exit status, wall duration, disk floor, bytes/rows, all input hashes, and raw logs. No broad process kill is used.

The runner clears inherited `VELOREN_NATIVE_REQUESTS` (the older Talk input), `VELOREN_RTSIM`, `VELOREN_TERRAIN`, `RTSIM_NOLOAD`, and `RTSIM_IGNORE_VERSION` so neither a Talk request stream nor alternate world/save paths or load bypasses can leak into the recruitment trial. The freeze JSON consumed by `run_pair.py` must pin the official source commit, source-patch SHA, Cargo.lock SHA, binary SHA, assets path, world seed and source-world hash, per-trial userdata manifest plus all eight payload hashes, view/persister UID lists, loopback-only settings hash, and all runtime limits. The runner rejects missing/mismatched hashes or shared userdata/output paths. No freeze JSON or native run output has been created by this package; those remain parent-reviewed after the adapter and unit tests are accepted.

## Stop/claim boundary

The Python tests establish interface and controller behavior only. They are not native execution evidence. A successful native request, sent message, accepted request, or terminal event alone is not completion. Preserve actual Job observations, terminal events, and post-hire native behavior. Report `PARTIAL` if the native job transition or subsequent autonomous behavior is absent; report no algorithmic advantage from this single uncontrolled-RNG pair.
